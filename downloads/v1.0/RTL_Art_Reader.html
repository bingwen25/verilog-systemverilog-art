Verilog/SystemVerilog 编程艺术

工业级 RTL 设计的原理、权衡与实践

版本：完整初稿 v1.0／2026-11-14
状态：六篇33章、附录A—G及三个工程案例正文已齐备；这是待出版审校的完整初稿，检查结果见文末验证记录。

本书的任务，是系统解释优秀 RTL 为什么如此设计，并让这些解释接受语义分析、反例、验证和实现结果的检验。

致读者

读懂一段 RTL，至少有两种程度。第一种是能够说出它在每个时钟沿更新哪些变量；第二种是能够解释：为什么这里需要保存状态，为什么这个接口允许背压，为什么这条路径必须被寄存，以及改变这些决定会破坏什么。

本书以第二种能力为目标。我们会学习编码方法，但不会把编码约定当作设计理由。一个方案值得采用，应当因为它在明确的约束下满足了需求，并使其正确性和代价容易检查。

读者应具备组合逻辑、触发器、同步时序电路和二进制运算的基础。本书主要面向数字 IC 的 RTL 设计；FPGA 读者也能使用其中的语义与结构分析方法，但存储器、复位、时钟资源及实现代价必须结合目标器件重新判断。

语言语义以 IEEE 1800-2023 为核对基准，示例优先采用常用的 SystemVerilog 可综合结构。这并不表示所有工具都支持该标准的全部特性，也不表示语言标准定义了统一的综合结果。每个完整工程最终都必须记录实际工具、版本、选项与目标平台。

正文含语义推演片段，配套工程另含完整RTL、轻量自检TB和运行入口。片段不能直接作为完整模块编译；只有执行记录明确列出的文件、配置与检查才具备相应证据。尚未执行的仿真、综合、形式化与物理检查不标为通过。

全书保持六篇、33章。组织顺序是：明确问题，掌握语义，选择结构，理解实现约束，建立正确性证据，完成工程交付。验证思维从第二章开始出现，第五篇再系统展开方法。

写作与证据约定

每个关键结论都需要回答四个问题：它依据哪种规则？在什么条件下成立？有什么反例？怎样检查？

第一篇　设计哲学与工程方法

第1章　RTL 编程的本质与设计哲学

1.1 一段代码背后有哪些硬件承诺

假设我们要在使能有效时累加一个寄存器：

always_ff @(posedge clk) begin
    if (!rst_n)
        count <= '0;
    else if (enable)
        count <= count + 1'b1;
end

这段片段假定 count 已声明为固定宽度的无符号变量，rst_n 与 enable 在时钟采样附近满足相应时序要求。复位虽然以 _n 命名，仍然是同步复位：敏感事件中只有 posedge clk。

从行为上看，每个上升沿选择三种操作：清零、加一、保持。若 count 为 W 位，加一的结果存入 W 位对象，超过可表示范围的部分被截断；这个计数器按模 2^W 回绕。若需求要求饱和，代码就不符合需求，即使它能合法编译并顺利综合。

从结构上看，我们需要保存 W 位状态，需要形成下一计数值，还需要选择保持、递增或清零。综合工具可能把选择逻辑映射为数据路径上的多路选择，也可能利用目标单元支持的使能等结构。源码表达的是行为约束，具体单元映射依赖库、约束和工具。

从系统上看，enable 来自哪里仍然没有答案。若它来自另一个时钟域，上述局部代码没有解决跨域问题。局部行为合理，不足以证明系统连接合理。

工业 RTL 的基本工作，就是把这些层次之间的关系写清楚，并持续检查它们是否一致。

1.2 RTL 是状态转移关系的可执行表达

对普通单时钟同步模块，可以用下面的模型思考：

[ S_{k+1}=F(S_k,I_k),\qquad O_k=G(S_k,I_k) ]

S 是采样边沿之间保存的状态，I 是当前输入，F 决定下一状态，G 决定输出。对寄存输出，应把对应寄存器纳入 S。这个模型是分析工具，不覆盖所有 HDL 构造；多时钟、异步复位和锁存器需要补充事件与时间假设。

在这个模型中，源文件里写在前面的模块实例不会因此先于另一个模块运行。不同过程并发响应事件；过程内部的语句顺序、表达式求值和变量更新，则由语言语义决定。“硬件并行”不能成为忽略赋值顺序和调度规则的理由。

例如：

always_ff @(posedge clk) begin
    a <= b;
    b <= a;
end

在其他驱动不存在、时钟采样没有竞态的前提下，右值使用该次过程执行时可见的值，非阻塞赋值安排随后更新。因此它描述两个寄存器交换先前的值。把第二行理解为读取第一行刚写入的新值，会得出错误结论。第7章将完整解释调度与竞态；这里先建立一个习惯：对寄存器分别写出“旧状态”和“下一状态”，不要用软件逐行更新的直觉代替推演。

1.3 四个问题不能互相代替

问题 判断依据 通过后仍未解决的事
代码是否合法 语言语法与语义规则 是否实现需求
仿真行为是否符合预期 激励、检查器、事件语义 未覆盖情形与物理时序
综合结构是否符合意图 综合报告、网表与目标资源 集成后的真实路径与功耗
工程实现是否合适 功能证据、约束、PPA、维护成本 不在证据范围内的配置与环境

一个计数器可以完全符合语言规则，却在结束判断上多等一个周期。一个仿真能通过的模块，可以因为测试没有施加背压而隐藏丢数问题。一个功能等价的资源共享实现，可以因为多路选择链变长而恶化时序。

“代码能跑”只回答了某个模型下、某组条件中的问题。评审时要把结论说到证据能够支持的位置。

1.4 为什么清晰度会影响正确性

假设一个接收模块有三个不同位置分别判断 valid && ready，其中一处又额外判断 !flush。这可能是合理设计，也可能意味着团队对“已接收”有两个定义。如果统一定义 accept，并在契约中说明 flush 是否阻止接收，就能让状态更新、计数器和检查器围绕同一个事件工作。

统一命名的价值在于暴露设计决定。然而，不能把所有输出都盲目绑定到同一个便利信号：若错误上报需要记录“被拒绝的尝试”，它检查的事件就不等同于接受。抽象必须保留语义差别。

可读性能够减少理解成本，但不构成功能证明。相反，过度压缩、隐藏优先级的代码，会让证明和修改的成本上升。

1.5 好方案来自约束下的权衡

考虑一个递增计数器的终值检测。直接比较当前值容易理解；提前保存“下一周期到终值”的预测标志，可能改变关键路径，却也增加状态及一致性义务。若终值允许运行中修改，预测标志还可能失效。

因此，“增加寄存器改善时序”需要继续追问：允许增加接口延迟吗？新寄存器保存的含义是什么？更新和取消时是否一致？面积与时钟负载是否值得？应先识别实际瓶颈，再进行有验证支撑的修改。

本书采用如下判断顺序：先满足正确性与硬约束，再比较实现效率、清晰度、可验证性和维护成本。不同项目可能得出不同结论。权衡不等于随意选择，它要求明确比较条件。

1.6 本章审查与练习

评审一个模块时，首先找到保存了什么状态、在哪些事件下更新、输入输出何时有意义，以及哪些行为依赖环境。再检查“保持”是否是有意行为，异常与正常事件是否有明确优先级。

练习：把本章计数器改为饱和计数器，先写出终值时 enable 有效的行为，再画出所需比较与选择结构。若有人声称饱和计数器一定比回绕计数器慢，请列出验证该结论必须控制的实验条件。

参考答案要点：饱和行为需要终值判断并抑制递增更新；这带来结构差异，但映射、位宽、布局和约束会影响最终时序，不能仅凭 RTL 宣称必然更慢。

第2章　从设计需求到 RTL 契约

2.1 模糊需求会变成隐藏的架构决定

“启动后等待 N 个周期，产生完成脉冲。”这句话没有说明启动何时被接受，N 是否包含启动沿，N=0 是否允许，忙时启动如何处理，以及取消和完成同时发生时谁优先。

这些问题必须得到答案。若设计者在编码时自行选择，验证者又采用另一种理解，双方即使都认真工作，也会得到不兼容的结果。

契约把模块的责任、环境的责任和允许观察的行为分开。它既是实现输入，也是验证输入。契约不是无限增加文档，而是把能够改变外部行为的决定放在编码之前。

2.2 案例 A：先冻结一个最小 Timer

第一版 Timer 使用单一时钟。所有控制和配置输入都属于该时钟域；复位采用低有效同步复位。异步来源的处理由集成方在模块外完成。本版不包含暂停、排队或自动重装载。

信号 方向 含义
clk、rst_n 输入 时钟与低有效同步复位
start 输入 启动请求电平；以采样沿上的值判定
period 输入 W位无符号周期数，合法值为1到2^W−1，W≥1
cancel 输入 取消当前操作；优先于启动与完成
busy 输出 当前保存着尚未完成或取消的操作
done 输出 完成事件对应的寄存脉冲，持续一个完整时钟周期

在上升沿到来前，若 rst_n=1、cancel=0、busy=0 且 start=1，本沿接受启动并锁存 period。环境必须保证接受启动时 period 合法且满足采样时序。运行期间修改 period 不影响已经接受的操作。这里计量的是时钟周期；对应的实际时间依赖时钟频率，不承诺独立于时钟的墙钟时间精度。

非法值0属于契约违例，验证环境应报告；不能在不同实现中默默解释成“立即完成”或“最大计数”。未来若需要硬件拒绝并报告非法配置，应显式增加相应接口与契约。

2.3 用边沿编号消除差一周期歧义

把接受沿记为 e0。对于在 e0 接受的 N，若没有取消或复位，在 eN 完成。接受沿本身不计为已经等待的一个周期。输出表中的值均为对应边沿寄存更新完成后的值。

N=3时：

边沿 本沿动作 busy done 概念性剩余周期
e0 接受，锁存3 1 0 3
e1 推进一次 1 0 2
e2 推进一次 1 0 1
e3 完成 0 1 0
e4 无新请求 0 0 0

N=1时在 e1 完成，不在 e0 完成。因此一个自然实现是接受时装载 N，在活动状态下每沿检查剩余值是否为1，否则递减。

注意语言中的“边沿后输出”与 SVA 中的“在边沿采样”不是同一个观察点。若 done 在 e3 的 NBA 更新后拉高，常规并发断言在 e3 的采样值仍是更新前的值，到 e4 才采到高电平。第27章会把这种观察差异显式写入检查器；不能看到波形标记就随意调整断言延迟。

2.4 同时发生的事件必须有唯一解释

优先级为：复位、取消、忙态推进、空闲态启动。

采样情形 约定行为
复位有效 清除活动操作，busy=0、done=0，不报告完成
取消与终值同时出现 取消生效，done=0
忙时出现启动 本沿忽略该启动，不锁存配置、不排队
完成沿同时出现启动 按沿前忙态处理，本沿不接受新操作
空闲时取消与启动同时出现 取消优先，不接受启动
start 一直保持高电平 每次重新空闲且无取消的采样沿都可再接受

最后一条尤其容易被误读。所谓“忙时忽略”，指忙时的采样不接受请求；若电平持续到空闲，它仍然满足新的接受条件。若希望每次高电平只启动一次，就需要边沿检测或握手协议，并重新定义复位后的检测状态。

本版完成沿不接收新请求，因此有一拍的接受间隔。更高吞吐的重启方案可以实现，但会改变优先级与验证场景，不应作为无声的局部优化混入第一版。

2.5 从契约导出状态，不从代码反推需求

Timer 至少需要表示活动与空闲，并在活动时记住剩余周期。可以独立保存 busy 与剩余数，也可以约定剩余数非零即为活动。

独立保存 busy 让接口含义直接可见，但需要维持 busy 与计数值的一致性。由剩余数推导活动可减少显式状态，却让0承担空闲编码，并可能把比较逻辑引入输出路径。是否有净收益需要结合具体结构和实现目标判断。

两种实现都应服从同一外部契约。内部变量名、递增还是递减，并不是接口要求。验证参考模型若逐行复制实现算法，就可能复制同一个错误；以接受沿与预计完成沿描述检查，更容易获得独立性。

2.6 让需求可以追踪到检查

编号 需求 检查场景或方法
T01 仅空闲且无取消时接受 空闲、忙态、完成沿分别施加启动
T02 接受时锁存周期 运行中连续修改外部配置
T03 在接受后第N个边沿完成 独立周期模型；覆盖N=1、2及最大合法值
T04 取消抑制完成 普通计数沿、终值沿分别取消
T05 复位终止操作 空闲、活动、终值附近复位
T06 完成脉冲单周期 连续观察完成与后续接受行为
T07 输入配置合法 接受事件处检查非零；非法激励单独归类

安全性要求例如“不接受忙态请求”“取消不产生完成”；有界完成要求则是“在没有复位和取消、时钟继续运行的条件下，接受后第N个边沿必须完成”。如果环境不断取消，不能无条件要求最终完成。

假设也可能掩盖错误。形式化环境若假设 start 永远为0，所有响应性质都可能空洞通过。因此除了断言，还要覆盖真实接受、N=1完成、最大周期完成与取消路径，并审查假设是否排除了应支持的行为。

2.7 契约的修改应当可见

后续增加 Pause 时，“N 个周期”就会产生两个候选含义：经过的全部时钟周期，或只计算未暂停的有效推进周期。增加自动重装载时，还要说明新周期来自原始配置还是最新输入。

每个功能扩展都应修改需求、周期表、状态模型和检查点。代码变化小，不代表契约变化小。

练习：允许在完成沿接受新请求，保留取消优先。写出接受条件、新旧配置的作用范围，以及 done 与 busy 同时为1是否允许。参考答案要点：完成旧操作与接受新操作可以同时发生，因而两输出可同高；必须区分旧操作终值和新配置装载，不能让新配置改变旧操作的完成时刻。

第3章　从 RTL 到硬件实现的完整过程

3.1 每一种工具只回答一定范围的问题

编译、展开、仿真、综合和物理实现常被画成单向流程。实际项目里，它们更像一组相互反馈的模型。接口契约约束实现，检查器检验行为，实现报告又推动架构调整。

最危险的误解，是把某一步的通过当作所有模型都通过。语法正确不等于可综合；可综合不等于满足时序；满足一个约束集合不等于约束本身完整。

3.2 展开决定我们究竟在检查哪个设计

参数、常量、层次绑定和 generate 条件决定实例化出来的结构。例如 FIFO 深度为1与深度为16，可能不只是容量不同：地址位宽、满空判定和存储推断都可能走不同路径。

$clog2(1) 为0，因此直接用 $clog2(DEPTH)-1:0 书写索引范围，不会自动得到一个符合设计意图的“零位地址”。保护位宽只能解决声明问题，不能代替深度1的行为设计。

一个参数化模块的质量证据，必须指向具体配置集合。只检查默认值，不能声称全部参数合法。应先界定支持域，例如深度是否必须为2的幂，再为边界值建立专门的展开与行为检查。

3.3 仿真检查时间上的行为

RTL 仿真依据语言事件模型执行。它擅长展示状态、输入与输出如何随激励演化，但激励与检查器共同决定能发现哪些错误。

“跑了很久没有报错”不是充分描述。Timer 即使连续运行一百万拍，若从未测试终值沿取消，仍然没有检查 T04 的关键冲突。测试时间、代码覆盖和需求覆盖分别描述不同事情。

时钟沿附近驱动输入、在寄存更新前读取输出，会制造测试平台竞态。应明确驱动与采样时机，通过合适的 clocking block 或受控相位组织来避免把执行顺序当作协议。第7章和第28章将给出具体写法。

四态仿真能够揭示部分未初始化或冲突问题，但 X 是模型中的未知值，不能直接模拟触发器亚稳态的模拟电压与恢复过程。没有观察到 X，也不能证明 CDC 安全。

3.4 综合把行为映射到目标结构

综合会优化布尔逻辑与状态结构，并映射到目标资源。代码中两个相似表达式是否共享、数组是否成为 RAM、FSM 使用何种编码，都受设置和目标平台影响。

因此应检查综合日志、推断结果、单元统计与关键结构，而不只观察“综合完成”。对 Timer，应确认计数位宽、比较逻辑、复位处理以及是否出现意外锁存器。对 FIFO，还要检查存储器读延迟和读写同地址语义是否与契约一致。

可综合代码不保证跨工具推断一致。项目可以规定受支持的模板，但应记录这是工具适配约束，而不是语言唯一正确写法。

3.5 STA 检查约束下的路径关系

静态时序分析围绕时钟、路径、库延迟与约束判断建立和保持等时序要求。RTL 设计者需要理解报告中的起点、终点、数据路径、时钟关系、扇出与负载，才能把报告映射回设计结构。

若一个路径未被约束，不能因为它没有被报告为违例就认为它满足要求。若把真实同步数据路径误设为 false path，报告可能更好看，硬件仍会失败。约束属于设计证据的一部分，必须评审。

综合阶段的估计能够帮助筛选方向；布局布线后的互连、拥塞和时钟树会改变结果。增加流水级可能缩短组合路径，同时增加延迟、寄存器和时钟功耗。只有契约允许，且整体收益得到测量，它才是有效优化。

3.6 正确性检查各自承担什么责任

方法 主要回答 必须关注的边界
Lint 是否存在可疑结构与规则违例 规则配置、误报与豁免依据
仿真 给定激励下行为是否符合检查器 场景覆盖、参考模型、竞态
属性形式验证 假设范围内性质是否成立 空洞性、约束完整性、证明深度与状态

等价性通过并不证明原设计符合需求，它证明的是双方在指定条件下保持了某种一致。若原设计有 Bug，重构后完全保留 Bug，也可能等价。属性证明则不自动覆盖没有写出的需求。这些方法需要共同支撑质量结论。

3.7 建立一次可复现的优化实验

设 Timer 的关键路径被怀疑来自终值比较。实验应先保存基线 RTL、配置、约束、工具版本和报告，再提出单一假设，例如“减少计数位宽是否缩短比较与递减路径”。

首先检查支持范围：如果运行时允许完整 W 位配置，减小位宽已经改变了功能。只有需求确实限制最大周期，且接口对越界有明确规定，才能继续比较。

修改后先检查行为保持，再执行同条件综合与时序分析；若涉及功耗，还需记录活动来源、工作负载和测量窗口。面积、频率、功耗的比较必须使用相同口径。没有真实执行结果时，应记录“待验证假设”，不能编造百分比。

实验记录至少包含：问题、假设、改动、配置、验证结果、实现报告、收益与代价，以及采用或拒绝的理由。失败实验仍然有价值，它能阻止团队重复尝试已经不适用的优化。

3.8 什么才算可以交付

一个模块的交付对象包括 RTL，也包括解释它应该怎样工作的契约、支持的参数配置、检查方法、工具约束、已知限制和未关闭问题。

质量门禁应有可判断的结果：通过、失败、未运行、经批准豁免。不要把“未运行”写成“不适用”，也不要把工具告警全部压成绿色状态。对真正不适用的检查，应说明为什么，例如单时钟模块内部没有跨时钟域，并明确该结论不替代顶层集成分析。

本书最终工程的完成条件是：从一份干净的工程副本出发，按照记录的依赖与命令重建检查结果，并能追踪每个重要需求的证据。教学工程的报告只证明其声明的工具与配置，不自动构成商业项目的 sign-off。

练习：某优化使面积减少8%，但输入约束、综合工具版本与基线不同。能否归因于 RTL 修改？参考答案：不能。需要恢复可比条件，或把多因素变化拆开；同时检查功能、延迟与支持配置是否改变。

第二篇　SystemVerilog 语言与硬件语义

第4章　数据对象与可综合 RTL 子集

4.1 类型描述值，对象种类描述连接和驱动

初学者常把 wire 理解为组合逻辑，把 reg 理解为触发器。这个映射会很快失效：一个 reg 可以在组合过程里完整赋值，从而没有存储；一个 wire 可以连接触发器的输出，从而承载时序状态的可观察值。

应当分开思考两个问题：对象能保存什么样的值，以及谁可以驱动它。Net 表示连接及其驱动解析，Variable 表示由相应赋值规则更新的对象。logic 是常用四态数据类型，不是“自动判断该信号需要什么硬件”的指令。单一驱动的设计中，它能减少许多旧式声明差别；需要多驱动解析的连接仍应明确采用 net。

wire logic shared_line;   // net，四态元素类型
logic      next_valid;    // variable，四态
logic [7:0] state_q;       // 是否为寄存器取决于赋值方式

端口还涉及方向、显式对象种类和类型的默认推导，不能仅凭 logic 一词判断全部端口语义。工程上对普通 RTL 明确输入输出类型，对需要变量端口语义的场合可显式使用 var，对双向和解析网络显式使用 net，并用项目支持的工具核对连接。

4.2 单写入职责为什么比“能够编译”更重要

假设一个进程因软件写操作修改计数器，另一个进程因硬件事件递增同一计数器。即使某个宽松工具接受这段代码，也没有建立一个清晰的同周期冲突规则。两个来源同时活动时，更新的含义不应由仿真执行顺序决定。

更好的结构是让两个来源产生请求，由一个状态更新过程决定优先级：

always_ff @(posedge clk) begin
    if (!rst_n)      event_count <= '0;
    else if (sw_wr)  event_count <= sw_data;
    else if (event_i) event_count <= event_count + 1'b1;
end

片段假设输入已同步、位宽相容，软件写优先是项目契约。它不证明软件写优先适合所有系统；它使这个决定可见，并能为同周期写与事件建立测试。若需求要求两者合并，就应明确规定新值为软件数据加一，而不是把两个赋值并排放置。

always_ff 对过程形式和其他写入者有约束，有助于发现职责冲突。但单写入也应体现在架构里：把整个模块塞进一个进程，仍可能让维护者无法理解更新关系。

4.3 二态与四态的选择包含信息取舍

bit 只能表达0和1，logic 能表达0、1、X、Z。把未知的四态值转成二态会丢失信息。用于参考模型的二态计数器可以方便计算；若在它之前就丢掉了 DUT 输出的 X，则错误可能被转换成一个看似正常的0。

因此，边界监测先检查未知值，再进行二态运算。控制信号、未初始化状态和总线数据在 RTL 中通常保留四态，以便暴露问题。二态仿真可能更快，但速度收益不能被解释为同等的未知态检测能力。

4.4 可综合是工具与目标的交集

语言允许动态对象、类、事件同步、队列和复杂时间控制，并不表示普通 RTL 综合能够把这些特性直接变成目标硬件。另一方面，也不能简单把所有 initial 或数组初始化说成不可综合：某些 FPGA 工具支持特定初始化形式，而 ASIC 上电行为通常需要不同的实现约定。

本书主路径采用固定结构、静态位宽、确定边界和无仿真延时的 RTL。验证专用代码放在单独文件或明确的构建文件集中。可综合函数没有等待时间，调用次数和参数结构应能在目标流程中展开为硬件；函数不是免费执行的软件子程序。

4.5 审查与练习

检查每个状态对象是否有唯一更新责任；每个多驱动连接是否有真实的硬件理由；声明是否意外依赖端口默认；二态转换是否隐藏 X；验证代码是否进入综合文件集。

练习：将计数器的复位、软件写、硬件清零和事件累加合并。先给出四者同时发生时的结果。答案要点：不存在脱离需求的唯一优先级；必须先冻结冲突契约，再用同一更新过程实现，并检查被低优先级事件覆盖是否允许丢失。

第5章　位宽、符号与表达式语义

5.1 算术正确需要明确运算域

在软件中，工程师可能习惯“整数足够大”。在 RTL 中，位宽既决定表达范围，也决定加法器、比较器、寄存器和连线的规模。一个八位对象可以表示无符号0到255，也可以表示二进制补码−128到127；相同位模式在不同运算域里有不同意义。

分析表达式时按四步进行：确定每个操作数的位宽与 signedness，区分自决定位宽与受上下文影响的子表达式，确定扩展与运算，再判断赋值处截断。不能把“先按操作数宽度计算，最后才看左值”作为通用规则；某些表达式会受到赋值上下文的反向影响。

5.2 把进位作为需求的一部分

logic [7:0] a, b;
logic [8:0] full_sum;
assign full_sum = {1'b0, a} + {1'b0, b};

这里显式把两个输入扩展到九位。这样读者无需依赖复杂的上下文推导就能看出：我们要保留完整无符号和。若输出只有八位，则应明确说明回绕或截断是预期行为。

不是每个表达式都应机械添加拼接。过多转换会使意图难读。关键在跨越边界处表达清楚：地址加偏移是否允许回绕、累加器是否保留进位、差值是否允许负数，以及最终输出采用饱和还是截断。

典型错误是把结果先放入窄临时变量，再赋给宽输出。扩展无法恢复已经丢掉的进位。另一个错误是先移位再希望目标扩展修复截断。应先在需要的宽度中形成操作数，再实施可能丢位的运算。

5.3 类型转换不是同一个旋钮

logic signed [7:0] s;
logic        [7:0] u;
logic signed [8:0] sx, ux;
assign sx = {s[7], s};
assign ux = {1'b0, u};

九位目标可以同时容纳 s 的全部有符号范围与 u 的全部无符号范围；之后在两个九位 signed 对象之间比较，数学含义就明确。若直接混合 signed 与 unsigned，运算规则可能使负数按无符号值参与比较。

$signed(expr) 改变表达式的符号解释，不等于任意增加位宽；$unsigned 同理。大小转换、类型转换、拼接和位选择分别有规则。一个 signed 向量的部分位选择通常作为 unsigned 结果参与表达式，不能假设符号属性沿着切片自动保留。拼接结果也应谨慎对待其无符号解释。

算术右移 >>> 是否复制符号位取决于左操作数的 signed 属性，不能只看操作符里有三个箭头。若一个 signed 值被放进无符号中间表达式，右移可能不再符合期望。

5.4 常量与参数也会改变结构

无尺寸十进制整数常量带有整数宽度与符号规则；与窄向量混用，可能意外扩大表达式。'0 和 '1 是常用的填充写法，但它们仍处在具体的表达式上下文中。给寄存器清零时 q <= '0 很清楚；在复杂运算里，不应仅凭外观推断最终宽度。

对计数容量 C，计数状态若要表示0到C，需要容纳 C+1 种值；地址只需要表示0到C−1。这两个宽度不是同一个公式。FIFO 深度为8时，三位地址足够，四位占用量才能表示8。把同一参数用于两者，是常见的满状态丢失原因。

参数化的位宽保护应先定义支持域。若 DEPTH 必须大于0，不能用一个表达式技巧让0“也能编译”后就宣称支持0。应在配置检查阶段拒绝不合法值。

5.5 以边界值验证算术

算术测试至少覆盖0、1、最大值、跨最高位、符号边界与溢出。对于加法，检查 255+1 比只检查 3+4 更容易暴露进位问题；对于 signed 比较，负数与高位为1的 unsigned 值组合尤为关键。

审查时把每个截断点标出来，并说明其意图。若工具报告位宽警告，先复算表达式，不要默认添加强制转换；一个转换可以消除警告，也可以正式固定错误结果。

练习：比较8位 signed 温度 t 与8位 unsigned 阈值 limit，阈值允许0到255。答案要点：把两者扩展到共同的九位 signed 域，前者符号扩展、后者补0，再比较；直接把 limit 转成8位 signed 会把128到255解释为负数。

第6章　四态逻辑与未知态处理

6.1 X 是缺失的信息

仿真中的 X 可能来自尚未初始化的状态、驱动冲突或显式未知赋值。Z 通常表示高阻驱动状态。它们是数字模型中的值，不能直接等同于真实电路的亚稳态、电压或某个“第三电平”。

一个无复位的数据寄存器在仿真开始时可能为 X。若协议保证对应 valid 为0，数据此时可以没有语义。这不意味着需要为了波形美观给整个数据阵列增加复位；应该检查未知数据是否会在 valid 有效时被消费。

这种区分直接影响面积、复位树和存储器推断。正确目标是使有效操作的数据已定义，而不是把所有内部信号强行变成0。

6.2 控制流可能掩盖未知

always_comb begin
    y = b;
    if (sel) y = a;
end

当单比特 sel 为 X 时，普通 if 不把它当作确定的真，因此该例走默认值 b。真实硬件若控制状态未知，可能选择 a 或 b；仿真给出确定 b，就可能过于乐观。

对单比特条件，条件运算符 sel ? a : b 在条件未知时，对两个分支逐位合并：相同位可以保留，不同位成为 X。它在某些多路选择模型中更能表达未知性，但不是所有 X 问题的万能修复。重汇聚路径可能产生相反的过度悲观现象；工具的 X 传播模式也会改变观察结果。

因此，未知传播模型与控制合法性检查需要配合。控制信号本不应未知时，可以在有效采样点检查 $isunknown(sel)，把错误报告在源头。

6.3 比较和通配不是同一回事

== 与 != 在含未知位、结果不能确定时可以产生 X；=== 与 !== 对 X/Z 进行逐位精确匹配，产生确定的0或1。后者适合 testbench 比较，包括检测输出是否出现意外未知。不能把它们当作所有 RTL 比较的通用替代品。

case 对四态进行精确匹配；casez 把 Z和问号作为通配，且需注意选择表达式中的 Z也可能被通配；casex 进一步把 X作为通配，容易把未初始化控制吞掉。本书普通控制路径避免 casex。

使用 unique case 既表达互斥/覆盖意图，也可提供运行期诊断与优化信息，但它不会自动建立安全恢复。若没有匹配分支且未定义默认行为，不同模型与优化假设可能暴露差异。不能把 unique 当作允许忽略非法输入的装饰。

6.4 X 检测要放在有语义的位置

数据总线在 valid 为0时允许无意义，不代表 valid 本身允许未知。应先检查 valid/ready 的控制合法性，再在确定发生传输时检查数据。

// 验证代码：假定此处只在完成复位后的采样点调用
assert (!$isunknown({valid, ready}));
if (valid && ready)
    assert (!$isunknown(data));

这是采样动作中的片段，不是完整 testbench。复位释放、初始化和驱动相位需要单独规定。若 valid 为 X，直接使用 if(valid) 可能跳过数据检查，所以控制检查不能省略。

综合中的 X 常被用作 don't-care，仿真中的 X却表示未知。把错误状态的输出设成 X可能帮助发现问题，也可能允许工具以任意值优化该状态。若项目要求故障状态输出确定安全值，就必须按该需求实现，不应以调试便利代替安全行为。

6.5 审查与练习

逐一询问：未知是否允许存在、何时不再允许、是否会被二态转换吞掉、是否被通配分支匹配、是否因复位假设而从未检查。对非法 FSM 状态，区分仿真 X检测、二进制非法编码恢复和实际故障模型。

练习：valid=0时 data=X是否是Bug？答案要点：取决于契约和下游是否真正以valid门控消费；若数据进入未门控的地址、控制或功耗敏感路径，仍有需要解决的影响。不能只凭波形的 X判断功能正确或错误。

第7章　事件调度与赋值语义

7.1 时间戳相同不等于动作同时可见

离散事件仿真把同一时间戳内的动作分配到事件区域。对本书常见 RTL，重点理解边沿事件触发后的过程执行、非阻塞赋值更新，以及并发断言的采样与求值。完整标准包含更多区域，本章的简化模型不能作为所有 program、PLI 或 clocking block 交互的替代说明。

阻塞赋值在过程语义中完成本次赋值后再执行下一句；非阻塞赋值在执行语句时求右值并安排更新，过程继续执行。二者名称没有规定物理路径传播需要多久。RTL 中使用 # 延时模拟“真实门延迟”，通常既不能建立可靠的综合契约，也不能修复架构问题。

7.2 跨过程读取不能依赖 Active 区顺序

always @(posedge clk) a = b;
always @(posedge clk) c = a;

若 a、b、c 没有其他驱动，两个过程在相同边沿触发。先执行哪个过程会影响 c 读到旧a还是新a，因此该写法把行为交给了不应依赖的调度顺序。

always_ff @(posedge clk) a <= b;
always_ff @(posedge clk) c <= a;

在无其他竞态的同步模型下，a与c分别取得边沿前的b与a，表达两级状态传递。非阻塞赋值的价值，是把本拍计算与状态提交分开。它不会修复错误的复位、异步输入或两个过程写同一对象等其他问题。

7.3 同一过程也需要清晰的数据依赖

always_ff @(posedge clk) begin
    if (!rst_n) q <= '0;
    else begin
        q <= q + 1'b1;
        if (clear) q <= '0;
    end
end

同一顺序过程对同一变量安排多次非阻塞赋值时，源语句顺序有明确作用；这里后面的清零覆盖前面递增的安排。它不是跨过程的确定优先级。工程上更直观的 if/else 往往更便于审查；多次赋值即使合法，也应避免隐藏优先级。

过程内临时计算可以使用阻塞赋值，然后以非阻塞赋值提交寄存状态，但临时量的作用域、赋值完整性与外部读取必须受控。不能把“组合阻塞、时序非阻塞”扩大成语言绝对禁令；它是降低竞态和理解成本的强推荐约定。默认采用简单模板，例外应能解释必要性。

7.4 为什么 #0 不是可靠同步机制

在 testbench 中把检查推迟 #0，只是移动到当前时间片的另一个区域，不等于“等所有非阻塞更新完成”。复杂的零延时循环还会让问题更难理解。

可采用明确的驱动和观察相位，例如在下降沿驱动、上升沿采样并按受控方式观察更新后结果，或者使用定义输入输出偏移的 clocking block。选择哪一种都必须说明采样对象是沿前值还是更新后的值。教学 TB 的小量采样延迟只是一种仿真观察手段，不是设计时序裕量。

7.5 断言采样与寄存输出的相遇

常规并发断言在时钟事件处使用采样值，性质在后续相关区域求值。DUT 同沿的 NBA 更新不会倒流进已经取得的采样快照。$past 与 $stable 等采样函数也应放在这个模型中理解。

例如 accept |=> busy 检查下一采样点的 busy；若 busy 在接受沿 NBA 后置1，它会在下一沿被采到1。若观察波形采用沿后值，而性质采用沿前采样，必须在文档里标记两种观察口径，避免把一个正确实现误判为差一周期。

disable iff 通常采用异步禁用语义，并非简单等价于时钟采样的普通前提条件。复位与断言采样同时间变化时尤应明确；第27章再讨论完整写法。

7.6 审查与练习

识别同沿交互的每个读写者，检查是否跨过程依赖阻塞更新顺序。不要用仿真中反复稳定得到某一结果来证明无竞态：一个模拟器版本的固定内部顺序也可能稳定地产生偶然结果。

练习：把两个进程合并会不会自动消除所有问题？答案要点：合并可以确定过程内部顺序，但可能改变原本希望表达的寄存级关系；应先写旧状态到新状态方程，再选择赋值形式，而不是以消除报错作为唯一目标。

第8章　组合逻辑的描述艺术

8.1 完整赋值表达无需记忆

一个纯组合输出应仅由当前输入和当前状态决定，不需要记住上次过程执行的结果。过程某条路径未赋值，就可能要求保持，从而引入锁存行为。

always_comb begin
    next_count = count;
    done_next  = 1'b0;
    if (busy) begin
        if (cancel) next_count = '0;
        else if (count == 1) begin
            next_count = '0;
            done_next  = 1'b1;
        end else next_count = count - 1'b1;
    end
end

片段假设 count 为合法无符号剩余计数；它只是下一状态组合计算，尚未包含启动与完整复位更新。next_count=count 不会因此推断锁存器，因为 count 是当前状态输入，next_count 在每次执行都有赋值；真正的状态保存发生在后续寄存器更新中。

默认值应表达意图，不是机械消除警告。输出默认0、下一状态默认保持、选择结果默认错误码，分别承担不同契约。

8.2 优先级是功能，树形结构是实现

if/else if 明确优先顺序。两个请求同时出现时，排在前面的获胜。若需求本来要求互斥，仍要对互斥条件建立检查，而不是期待综合自动识别输入不可能同时出现。

独立 if 对同一对象依次赋值也会形成覆盖关系，但阅读成本更高。case 的分支比较和 unique 等修饰影响语义与工具假设，不能简单宣称“case一定是并行逻辑，if一定是串行逻辑”。工具可以重新优化满足语义的网络。

若优先级编码器位数很大，关键路径可能由选择链主导。重组为分层选择、预译码或流水线，需要考虑真实综合结果，也需要保留相同的获胜规则。

8.3 always_comb 不是自动求解器

always_comb begin
    c = b;
    b = a;
end

这段先读 b再写 b，容易让仿真结果依赖先前的 b值。always_comb 对隐式敏感项有专门规则，块内写入的表达式不会像直觉中的“任何变化都再算一遍”那样自动使过程自触发。工具可能警告先用后赋值。正确组织通常是先计算依赖项，再计算使用者：先 b=a，再 c=b，或者直接表达各自从 a推导的关系。

更深的组合环，例如 a依赖b、b又依赖a，也不会被关键字自动变成可实现设计。若设计确实需要反馈存储，应使用明确的存储结构与时序模型，而不是靠零延时迭代收敛。

8.4 函数与循环隐藏不了硬件规模

一个静态边界的 for 循环通常描述重复结构或组合依赖。循环写一行不意味着只用一个加法器反复执行。若每次迭代依赖上一次累加，综合可能形成较长的加法链或重新平衡网络。

函数让代码聚焦在意图，但调用多个函数也可能复制硬件。若希望跨周期复用一个算术单元，应显式设计调度、操作数选择和状态，不应把函数调用当成软件调用栈。

审查项：所有路径完整赋值；默认值有理由；优先级可见；没有读后写顺序陷阱；循环规模有上界；组合输出没有形成接口间闭环。

练习：把16路求和写成一个循环一定比树形写法省面积吗？答案：不能由源码长度推断。需比较运算位宽、结合规则、工具优化和目标时序；若有逐步截断，两种结构还可能不等价。

第9章　时序逻辑的描述艺术

9.1 每个寄存器都应能回答“何时改变”

寄存器更新有四种常见来源：复位、初始化/装载、正常推进、保持。把这些来源写成清晰的优先关系，有助于发现被覆盖的事件与不必要的更新。

always_ff @(posedge clk) begin
    if (!rst_n) begin
        valid_q <= 1'b0;
    end else if (in_ready) begin
        valid_q <= in_valid;
        if (in_valid) data_q <= in_data;
    end
end

这里 data_q在无有效输入时保持，valid_q决定它是否有意义；代码假设 in_ready已依据槽位空闲或下游接收条件正确产生。data_q没有复位，属于有意选择，不能在valid_q=0时将其作为有效数据使用。

只复位控制状态可以减少复位负载，并改善某些存储资源推断；但如果数据寄存器会驱动外部安全输出、地址或不受valid门控的功能，就必须重新审查该选择。

9.2 使能保持与反馈多路选择

else if(enable) q<=d 描述 enable为0时保存状态。目标实现可能采用带使能触发器，也可能在输入处形成反馈多路选择。它不会自动意味着时钟被关断。

数据使能与时钟门控对时钟树活动的影响不同。手写 clk & enable 可能产生毛刺和不满足时钟质量的脉冲；门控需要正确的集成单元、使能锁存与测试控制，详见第21章。

是否应在 enable=0时给 q显式写 q<=q，通常不改变功能。省略自赋值让“没有更新”的意图更直接；某些团队可能采用不同风格，但不能把自赋值有无说成功能规则。

9.3 复位不只是初值

同步复位需要时钟采样才生效。异步复位可在时钟之外触发状态更新，但释放涉及恢复/移除时序及域内一致性。二者不能仅按“同步更简单”或“异步更安全”选择；上电、时钟可用性、库单元与系统恢复要求都会影响决策。

复位过程中是否允许 ready有效，输出是否允许组合依赖输入，复位打断事务后是否仍有迟到响应，都是接口问题。把所有寄存器清零，并不能自动解决事务一致性。

9.4 多拍状态的相互一致

若一个事务包含 valid、地址和数据，三者的更新必须服从同一个接受事件。地址在start时锁存、数据在下一拍锁存，如果环境没有承诺保持数据，就可能拼接成两个不同事务。

应先定义捕获事件，再检查所有成员是否在该事件中一起建立。控制状态可能只占一位，但它承担的数据生命周期语义往往比数据本身更重要。

代码组织可以按寄存器职责分进程，也可以把强关联状态放在一个进程；不是进程越少越好。关键是每个对象单写入、关联事件一致、默认保持清楚，以及评审者能局部理解优先级。

9.5 审查与练习

为每个寄存器列出复位值、更新条件、保持条件与有效性条件。检查复位释放前后是否出现未经初始化的数据消费；检查同周期完成、取消、启动是否由一致规则处理。

练习：把data_q也复位是否一定更可靠？答案：可能使仿真更确定，但也可能增加复位树代价、限制RAM推断，且掩盖valid协议错误。可靠性需要以实际需求、数据可观察路径和系统复位策略判断。

第10章　结构化数据与语言抽象

10.1 抽象应维护语义关系

地址、命令和属性共同构成一个请求，分别在多个端口间传递容易漏连。packed struct可以把固定宽度字段组织成整体：

package req_pkg;
    typedef struct packed {
        logic [15:0] addr;
        logic [31:0] data;
        logic        write;
    } req_t;
endpackage

结构体让关联关系可见，也使整体赋值更方便。但字段增加会改变布局、位宽和接口依赖。跨模块、外部工具或软件生成物使用的布局，应明确规定，而不是依赖维护者猜测拼接顺序。

packed表示位级连续表示；unpacked数组强调元素集合。logic [7:0] mem [0:15] 是16个八位元素，不应与一个任意排列的128位向量混淆。RAM推断还依赖读写过程形式、端口数量与目标工具模板。

10.2 Enum 提供类型意图，不提供自动恢复

typedef enum logic [1:0] {IDLE, RUN, ERROR} state_t;
state_t state_q, state_d;

显式状态类型方便诊断和阅读，但第四种编码仍然存在，X也仍然可能出现。默认分支可以指定对非法编码的响应，工具是否保留该逻辑又取决于故障模型、状态重编码和优化设置。

若需要抗单粒子翻转能力，必须定义可检测故障、恢复行为和编码策略，并结合实现验证；不能单凭 enum与default就称为容错FSM。

10.3 Package 管理共同含义

包适合保存共同类型、常量和无状态函数。过度把所有模块参数放进一个全局包，会造成不必要的依赖：一个局部配置修改可能迫使大量模块重新编译，甚至使不同实例无法采用不同配置。

局部参数表达模块内推导；实例参数表达可配置接口；包常量表达工程范围的共同约定。三者的作用域应匹配设计责任。编译文件集需要先处理依赖包，不能依赖某个开发者机器上偶然的编译顺序。

10.4 Function 和 Interface 的边界

纯组合函数适合集中位操作、校验与地址转换。可综合函数不能把等待事件隐藏在内部；任务是否受支持及其限制需核对工具，普通RTL通常优先使用无时间控制的函数和清晰过程。

interface与modport可以组织端口集合和方向视图，减少连接错误；但它们不会自动检查完整的时序协议，也不会替代CDC。不同工具对接口数组、参数化接口与层次引用的支持存在差异，跨工具交付前要做最小工程验证。

抽象的收益应超过定位成本。只有一个字段的简单端口也包进多层接口、让状态更新穿过许多函数，会使调试困难。适当抽象让语义更近，过度抽象让语义藏得更深。

10.5 审查与练习

检查结构体是否真正表达共同生命周期；包是否过度全局化；函数是否有隐含外部依赖或副作用；接口是否把方向与协议假设混在一起；工具支持是否有证据。

练习：把请求valid放进payload结构体是否总是更好？答案：不一定。valid承担传输控制，payload承担数据含义；如果接口采用独立ready/valid，通常保持控制关系显式更便于组合路径与背压分析。若整体结构确实统一保存，仍需说明valid的生命周期。

第11章　参数化与 Elaborate-Time 设计

11.1 参数化是扩大承诺范围

一个固定深度8的FIFO与支持任意深度的FIFO，不只是相同代码加一个parameter。支持范围扩大后，地址绕回、计数位宽、存储推断、深度1与吞吐性能都必须重新检查。

参数不应暴露内部每一个选择。把状态编码、内部比较器分层和所有临时位宽都做成公开配置，会增加无意义的组合数量。公开参数应对应使用者需要做出的选择，并有明确合法域。

parameter int unsigned DEPTH = 8;
localparam int unsigned AW = (DEPTH <= 1) ? 1 : $clog2(DEPTH);
localparam int unsigned CW = (DEPTH <  1) ? 1 : $clog2(DEPTH + 1);

这是位宽推导片段。DEPTH=0仍然非法，需要构建或验证时拒绝；AW保护只防止声明出现不期望范围，并没有赋予零深度硬件任何定义。

11.2 Generate 选择结构，运行时控制选择行为

generate条件在展开阶段决定哪些实例和连接存在；普通if根据运行时信号选择更新或输出。若某个参数固定为false，相应generate分支可以完全不存在；不能在运行时读取一个信号来动态创造模块实例。

用generate实现深度1特例有时能简化结构，但每个分支都需要检查。默认配置从不展开的代码，可能长期隐藏语法、连接或位宽问题。CI配置矩阵应覆盖每个结构分支，而不只是选几个数值。

11.3 宏适合文本开关，不适合隐藏类型系统

宏在预处理阶段替换文本，没有普通变量的作用域与类型保证。参数更适合实例配置，函数更适合有类型的计算，包更适合共享定义。宏可以管理工具适配或构建开关，但应限制命名空间和副作用。

若同一个宏改变RTL与TB两边的含义，两边可能一致地出错。验证模型最好从明确规格推导，而不是共享全部实现细节。共享合法范围和接口类型合理，共享核心算法则要审查独立性。

11.4 配置矩阵要围绕结构边界

FIFO可选择深度1、2、3、典型2幂和最大受支持值；数据位宽可选择1、非典型值及常用总线宽度。测试重点是公式与分支的边界，不是盲目穷举所有参数笛卡尔积。

对于只支持2幂深度的异步FIFO，深度3应该被明确拒绝，不能因为编译成功就纳入支持集。对大容量配置，即使功能正确，组合读数组也可能不适合目标RAM，参数化说明还应包含实现限制。

11.5 审查与练习

检查公开参数是否必要、合法域是否可检查、推导是否存在0宽/溢出、每个generate分支是否执行过、接口位宽与内部配置是否一致，以及支持声明是否超出实际证据。

练习：一个模块支持W=1到64，是否只需测试1和64？答案：若内部存在按字节分组、取整、generate或特殊算术，结构边界可能出现在8、9、16等位置。应检查公式与分支，选择能触发不同结构的配置，而不只测区间端点。

第12章 有限状态机：让控制流程可读、可证明

有限状态机（FSM）把“当前处于什么阶段”显式编码，再依据输入决定下一阶段及输出。它的价值不是把所有控制逻辑硬塞进 case，而是让状态空间、转移条件、非法状态行为都能被枚举和审查。工业设计中，状态名常常承载协议含义：IDLE 表示可以接收命令，WAIT_RSP 表示请求已发而响应未到，RESP 表示响应保持到被接收。若把状态写成含糊的 S1/S2，代码虽可综合，评审和波形调试却失去语义锚点。

以下是一个两阶段请求应答控制器。请求只在 IDLE 且 req_valid 时接受；响应阶段 rsp_valid 保持，直到 rsp_ready 同周期为 1。这里用 Moore 风格输出，使 rsp_valid 的逻辑值只依赖寄存状态，而不直接依赖输入组合毛刺。但状态寄存器各位到达时间、译码路径和布线延迟仍可能让组合输出在状态改变附近出现瞬态；若接口要求无毛刺输出，应再寄存输出或采用经时序审查的编码与译码结构，不能仅凭 Moore 命名保证物理无毛刺。同步复位在时钟沿将状态置为 IDLE。

typedef enum logic [1:0] {IDLE, WAIT_RSP, RESP} state_t;
state_t state_q, state_d;

always_comb begin
  state_d = state_q;
  unique case (state_q)
    IDLE:    if (req_valid) state_d = WAIT_RSP;
    WAIT_RSP: if (core_done) state_d = RESP;
    RESP:    if (rsp_ready) state_d = IDLE;
    default: state_d = IDLE;
  endcase
end

always_ff @(posedge clk) begin
  if (!rst_n) state_q <= IDLE;
  else        state_q <= state_d;
end

assign req_ready = (state_q == IDLE);
assign rsp_valid = (state_q == RESP);

代码的一处常见错误是仅凭 req_valid 转移，而没有要求 req_ready。在 ready/valid 语义中，valid=1, ready=0 并未发生传输。若上游因背压把 valid 保持三个周期，FSM 却在第一个周期离开 IDLE，控制器可能把请求当作已接收，数据寄存器却没有锁存，造成“控制进了下一阶段，数据还留在旧值”的错配。修正方法是定义 req_fire = req_valid && req_ready，所有“接受请求”的副作用都只受 req_fire 驱动。

状态编码常见 one-hot、二进制和工具自动选择。二进制用较少触发器，适合状态少、面积敏感且译码不在关键路径的模块；one-hot 状态位多，但常让状态译码直接成为单比特，可能改善时序，也可能增加时钟负载和复位网络。不要在可移植 RTL 中把“编码一定如此”当成行为保证。AMD Vivado 文档说明其综合流程可选择 FSM 编码方式，并提供 FSM_ENCODING 属性控制；这属于特定工具能力，约束属性应和目标综合器版本一起管理。工具若未识别 FSM，常见原因包括状态寄存器被算术改写、多处驱动、状态信号对外可观察、复位/默认逻辑不完整。应看综合报告确认实际识别和编码，而非从源代码猜测。

同步复位与异步复位的取舍要从系统复位架构出发。同步复位容易保持时序路径一致，但复位必须覆盖有效时钟沿；异步复位可在时钟停止时立即置位，却要求释放时满足恢复/移除时间，跨域释放需要同步处理。不能在 FSM 中混用无意的异步事件和同步数据路径。always_ff 用于表达唯一时序过程，always_comb 用于完整组合赋值；组合块先给所有输出默认值，避免遗漏分支推断锁存器。unique case 是设计意图和仿真检查提示，不等于自动修复非法状态；若工具对 unique 有不同解释，应依据语言标准和工具手册确认。

非法状态处理也是安全设计决策。default: state_d = IDLE 只能使下一个时钟沿回到空闲，不能保证非法状态下组合输出安全，所以输出解码也要有安全默认值。若错误状态可能造成外部副作用（例如重复发起写入），应直接规定“非合法状态时禁止 valid、写使能和提交脉冲”，再由故障检测或复位策略处理。若为形式验证加入状态合法性断言，应明确复位解除后的适用窗口，避免把复位期间的未知值误判成设计缺陷。

周期推演：复位沿后 state_q=IDLE；周期 A 中 req_valid=1、req_ready=1，该沿接受请求并进入 WAIT_RSP；周期 B 等待核心完成；若 core_done 在 B 采样为 1，沿后进入 RESP；周期 C 即使 rsp_ready=0，rsp_valid 继续为 1；当某一沿 rsp_ready=1，传输完成并沿后回 IDLE。响应数据必须在整个 rsp_valid && !rsp_ready 区间保持稳定，否则消费者看到的数据会随背压漂移。

设计检查清单：逐项列出状态、进入条件、离开条件和状态输出；确认每个请求/响应只在握手时发生一次；组合块有默认赋值并无锁存器；复位后状态与副作用输出都安全；非法状态的恢复路径明确；状态是否暴露给模块边界；综合报告是否识别预期 FSM；状态覆盖与转移覆盖包含等待、背压、同时事件和非法状态。安全关键路径还应审查状态翻转导致的瞬态输出，以及是否需要寄存输出。

练习：上例在 RESP 期间若 core_done 再次脉冲，是否会额外生成响应？答案：不会，因为当前状态只检查 rsp_ready，完成脉冲没有状态转移效果；但若核心可能每周期改变响应数据，必须在 core_done 时锁存响应数据，并在 RESP 背压期间保持。练习二：将 req_ready 改成 state_q==IDLE 后，如果上游在 ready 拉高时下周期撤销 valid，是否算已提交？答案：不算。提交发生在实际采样沿上的 valid 与 ready 同时为 1，不能由“ready 曾经拉高”推断。

第13章 计数器、定时器与事件：把时间契约写进位宽

计数器看似只是 count <= count + 1，真正的工程问题却是：从哪个沿开始计时、边界值是否包含、溢出时发生什么、事件输出是一拍还是电平、配置何时生效。把这些语义写清楚，能够避免典型的一拍偏差。本文定时器契约固定如下：同步低有效复位；空闲态遇到 start 时接受并锁存输入 N，要求 N>=1；接受沿之后的 N 个时钟沿完成；取消优先于完成；忙时 start 忽略；done 是单周期脉冲。输入 N 在接受时采样，之后变化不影响当前定时。

下面的实现采用“剩余沿数”计数：接受 start 的沿只锁存 N，尚不计为 N 个后续沿；此后每个忙态采样沿消耗一个周期。若剩余数为 1，在该沿产生 done 并回到空闲。因此 N=1 时，启动沿后紧接的下一个有效沿完成。取消在该沿优先，哪怕倒计数恰为 1，也不产生 done。

parameter int unsigned W = 16;
logic busy_q;
logic [W-1:0] left_q;
logic done_q;

always_ff @(posedge clk) begin
  if (!rst_n) begin
    busy_q <= 1'b0;
    left_q <= '0;
    done_q <= 1'b0;
  end else begin
    done_q <= 1'b0;
    if (!busy_q) begin
      if (start && !cancel && (n_in != '0)) begin
        left_q <= n_in;
        busy_q <= 1'b1;
      end
    end else if (cancel) begin
      busy_q <= 1'b0;
      left_q <= '0;
    end else if (left_q == {{(W-1){1'b0}},1'b1}) begin
      busy_q <= 1'b0;
      left_q <= '0;
      done_q <= 1'b1;
    end else begin
      left_q <= left_q - 1'b1;
    end
  end
end
assign done = done_q;
assign busy = busy_q;

片段假定 n_in 宽度正好为 W；若 W 是参数，须约束 W>=1；W=0 会导致负重复数和非法计数器宽度。工程代码也可写成 left_q == W'(1)，但尺寸化常量语法支持需与目标工具版本确认。也可以将比较写成 left_q == 1，SV 会按表达式尺寸规则扩展；要留意无符号/有符号混算。上面为突出意图，N=0 被忽略，接口契约要求调用者给非零值。若要将 0 定义为“立即完成”或“禁用定时”，必须改写行为并验证边界。

周期表如下，其中 N=3，A 为接受 start 的时钟沿；cancel 取值为 0：

采样沿 沿前状态 动作 沿后状态 done
A 空闲，start=1 锁存 3 忙，left=3 0
A+1 忙，left=3 消耗第 1 个后续沿 忙，left=2 0
A+2 忙，left=2 消耗第 2 个后续沿 忙，left=1 0
A+3 忙，left=1 消耗第 3 个后续沿 空闲 1

错误推演：若在 start 同一时钟沿进入忙态，并在 busy 分支的同一时序块里立即对旧 left_q 减一，非阻塞赋值右值读到的是沿前的旧计数；第一次运行可能从 X 或先前任务残值开始。即便额外用分支绕过 X，若启动沿也当作第一个计时沿，N=3 会在 A+2 完成，违反契约。另一种常见错误是 if (left_q==0) done<=1; else left_q<=left_q-1;：从 N 开始会先减到 0，之后才完成，实际产生 N+1 个后续沿。定时器须先定义计数表示，再从 N=1 手工走波形。

取消优先意味着 cancel 与终点同时为 1 时，不发 done。若产品需求是“已到期不可取消”，优先级反过来，并且系统上游必须知道这一点。忙时忽略 start 也意味着不能简单地把 start 当成重新装载；如果需要可重触发，另设 restart 或明确 start 对当前事务的作用。配置输入锁存使启动后软件改写周期值不扰动运行中的定时。

定时器和事件脉冲有不同职责。done_q 是寄存器，默认每拍清零，仅完成分支置一，所以单周期；若将 done 写成 busy && left_q==1 的组合信号，它会在完成沿之前整个周期有效，语义可能仍可用，但相邻逻辑采样时序和取消优先更易出错。跨时钟域不能直接采样单周期脉冲，脉冲可能比目的域时钟短或落在采样边沿之间；应使用脉冲展宽、toggle 同步、请求应答握手或异步 FIFO，选择取决于吞吐率和能否背压。

计数器位宽要由最大值推导。表示 0 到 M 的计数至少需要 $clog2(M+1) 位，但 $clog2(1)=0 会生成零宽向量，需封装 localparam CW = (M < 2) ? 1 : $clog2(M+1);。若只数 1 到 M，还要确认终值、减法回绕和加载值。事件累计器如果每拍可能同时发生多个事件，单比特增量不足；若一个周期可发生最多 K 个事件，应加 K 或使用分组计数，定义饱和还是回绕，并算出最长未清读窗口内的最大总量。

实现权衡：倒计数比较终值 1，易对应“还剩几个沿”的契约；上计数器比较 N，则要保存目标值和当前值，比较器可能在关键路径；预分频器可减低主计数器翻转，但会引入分频相位与重配置语义。共享计数器能节省面积，却让多个事件的独立暂停、取消、装载相互耦合。对于必须精确到输入周期的定时，应直接使用同一时钟域计数，不把逻辑分频器误当成新时钟树。

检查清单：文档写明 N=1、N=0、最大 N；start/cancel 同拍优先级；busy 状态 start 的处理；计数器的接受沿是否计入；done 是否只打一拍；复位时是否清 done 和 busy；参数宽度是否出现零宽；减一是否可能回绕；动态输入是否已锁存；跨域事件是否经过可靠传递。练习：N=4 且在 A+2 沿 cancel=1，done 在哪一拍？答案：A+2 沿取消生效，busy 清零且 done 保持 0；后续不再产生完成。练习二：如需忙时 start 忽略但记录一次待办，增加一个 pending 位，并在当前完成/取消后的空闲周期决定是否用已锁存参数启动，不能偷偷改变原本 start 接受契约。

第14章 握手协议：让每次传输都有唯一的采样点

ready/valid 是同步数据接口的一种常用协议。源端以 valid=1 表示当前有一个可传输项目，并在未握手期间保持 valid 和负载稳定；宿端以 ready=1 表示当前周期愿意接收。只有采样沿上 valid && ready 同时为真才发生一次传输。此规则看似简单，却决定了计数、FIFO 写使能、地址递增、标签分配都必须统一由同一个 fire 条件驱动。把 valid 的上升沿、ready 的上升沿或状态改变当作传输事件，会在背压下重放、丢弃或错配数据。

logic fire;
assign fire = valid && ready;

always_ff @(posedge clk) begin
  if (!rst_n) begin
    accepted_q <= '0;
    payload_q  <= '0;
  end else if (fire) begin
    accepted_q <= accepted_q + 1'b1;
    payload_q  <= data;
  end
end

握手发生在采样沿。若周期 P 的组合值为 valid=1, ready=0，没有事务；源端必须保持数据，宿端可在 P+1 拉高 ready，随后沿上才采样一次。若源端在 P+1 握手前就撤销 valid，即使它“看到之前 ready 低”，也违反承诺。若宿端在一次握手之后立刻保持 ready 高，源端可以在相邻周期送另一个项目，实现每周期一笔；valid 不必回到 0 作为分隔符。valid 表示一个持续存在的项目，不是脉冲事件。

反压设计要看组合路径。纯组合地把下游 ready 穿透多个模块，会形成长组合链；反过来若每级只在本地寄存 ready，却没有容量吸收迟到的一拍，可能发生溢出。一个简单单槽寄存器采用“当前空，或当前数据会被取走”作为 ready：in_ready = !full_q || out_ready。同拍旧数据握手并接收新数据时，存储寄存器更新成新数据，满位维持 1，从而无气泡接续。

assign in_ready = !full_q || out_ready;
assign out_valid = full_q;
always_ff @(posedge clk) begin
  if (!rst_n) begin
    full_q <= 1'b0;
  end else begin
    unique case ({in_valid && in_ready, out_valid && out_ready})
      2'b10: begin full_q <= 1'b1; data_q <= in_data; end
      2'b01: full_q <= 1'b0; end
      2'b11: begin full_q <= 1'b1; data_q <= in_data; end
      default: ;
    endcase
  end
end
assign out_data = data_q;

这里 out_data 在 out_valid=0 时无意义。若下游把无效数据也视为安全敏感信息，应将数据复位或屏蔽，但这会增加复位扇出和面积；协议本身不要求无效负载为零。上述 in_ready 直接组合依赖 out_ready，在单级可接受，在多个模块直串时可能形成组合环路或时序路径过长。可用 skid buffer、两项弹性缓冲或寄存切断 ready 链，但需保证“下游 ready 已下降而上游本周期仍送来的一项”有落点。

错误推演：模块以 if (valid) count++ 计收包数量，消费端 ready 连续拉低三拍。源端按照协议保持 valid 与 data，这三拍中模块把同一包计三次。正确条件是 valid && ready。另一种错误是 valid 只打一拍，碰上 ready=0 就消失：该事务无论后续 ready 如何都丢失。第三种错误是数据在 valid && !ready 时更新，消费者最终握手到的是不同于源端初次声明的数据；这是一种协议级竞态，而不是单纯的仿真波形问题。

多通道协议要定义独立握手还是原子组合。若地址、数据、字节使能在不同通道，则每个通道分别有 valid/ready，不能假设地址握手必然意味着数据握手；协议可能允许两者先后到达。若一个命令的多个字段必须原子接受，应在内部缓冲独立通道并在所有字段齐备时组装，或者采用单一打包通道。AXI 等标准总线有自己的时序、响应和 outstanding 规则，不能从简化 ready/valid 示例直接推断全部总线行为，应查对应官方规范。

valid 和 ready 的产生逻辑还要避免组合环。两个模块若各自 valid = !peer_ready、ready = !peer_valid，可能出现环路或无法初始化。工程规范通常要求源端的 valid 不依赖对端 ready，方便组合审查；具体协议也可能允许局部组合依赖，但系统需验证不存在零延迟循环。吞吐率由每周期握手数决定，延迟则由寄存级数决定；增加缓冲通常提升容忍背压能力，可能增加最坏延迟，但并不必然降低稳态吞吐。

检查清单：只有 fire 驱动副作用；停顿期间 valid 和负载稳定；复位时 valid 清零；同拍出入是否支持；ready 反压是否能传播或被缓冲；是否有组合环和过长 ready 链；多个逻辑副作用是否使用完全相同的握手条件；协议空闲周期的 data 是否允许任意。练习：valid 连续为 1 四拍，ready 为 1、0、0、1，则传输了几笔？答案：两笔，分别在第 1 与第 4 个采样沿。练习二：当缓冲满且本拍下游 ready=1、上游 valid=1，是否能同拍出旧值、入新值？答案：可以；旧数据被消费，新数据写入缓冲，沿后仍满且输出变成新值。

第15章 流水线与弹性缓冲：在吞吐、延迟和背压之间取舍

流水线把长组合运算切成若干级，用寄存器分隔逻辑深度。流水线能够提高可达到的时钟频率，并在填满后每拍接收/产生一笔，但“流水线每拍输出一个结果”只在没有停顿且每级可以推进时成立。加入反压后，必须阻止上游覆盖未消费数据，或提供额外存储接住已经在路上的项目。弹性流水级以 valid 标记寄存数据是否有意义，以 ready 表示本级有空间接收新数据。数据、valid 和 sideband 标签（例如 ID、错误标志、最后一拍）必须作为一个整体推进。

单级弹性寄存器的核心条件是 in_ready = !valid_q || out_ready。当本级为空时可以接收；本级满但下游同拍取走，也能用新数据替换。代码见第14章单槽示例。把它扩展到多级，若每级的 ready 组合反传，延迟可低而组合链增长；若 ready 寄存化，则每级多一拍反压传播延迟，通常需 skid buffer 保存额外一笔。设计目标不是抽象地追求“零泡”，而是给出可实现的频率、容量、延迟和最大反压延迟契约。

两级管线的一个推演：P0 时两级皆空，上游在沿 0 握手输入 A，沿后第一级存 A；沿 1 第一级把 A 推进到第二级，同时上游握手输入 B，沿后第二级为 A、第一级为 B；沿 2 下游握手 A，同时 B 推进到第二级、上游握手输入 C，沿后第二级为 B、第一级为 C。无背压时，首结果在沿 2 可见，随后每拍都能完成一笔输出并接受一笔输入，展示了两级管线的满吞吐。若沿 2 下游 ready=0，第二级必须保留 A；第一级也不能把 B 覆盖掉，因此反压回到上游，或者局部额外容量保存 B。一个看似“只要停住最后一级”的改法，会让第一级仍在推进并覆盖多个在途事务，数据丢失。

拆分组合逻辑时，还要明确每一级的运算延迟和标签对齐。若乘法结果流水化两拍，而异常标志只打一拍，异常标志就会和错误的数据配对。用结构体打包字段可以减少漏接风险：

typedef struct packed {
  logic [31:0] result;
  logic        overflow;
  logic [3:0]  tag;
} pipe_item_t;
pipe_item_t stage_q;
logic stage_valid_q;

每个被接受的 item 应满足顺序不变、恰好输出一次，除非模块明确允许丢弃或取消。若设计包括 flush（分支错误、复位或事务取消），必须说明 flush 清掉哪些级、同拍新输入是否接受、已对外承诺的响应如何处理。仅清 valid 通常足以使内部数据无效，但若输出 valid 已对消费者握手，就不能再撤销该笔事务。flush 若跨越多级组合网络，应检查所有有效位同步清除以及清除优先级。

弹性缓冲和传统固定延迟流水线各有适用场景。固定延迟流水线的控制简单、时序行为可预测，适合每拍必有数据或整体停机的运算核；ready/valid 弹性流水线适合上下游速率不一致、突发输入或系统级反压，但控制逻辑和形式性质更多。弹性级可以插入到已有路径切断时序，不必修改事务语义；但如果外部协议要求固定时延，插入缓冲改变可观察行为，需要评估。宽数据总线上的多个小 buffer 会消耗寄存器面积，RAM FIFO 更节省面积却可能有同步读延迟和不同满空语义。

错误推演：有一条 3 级管线，每级仅在自身 valid 时更新数据，且第二级停顿时第一级继续工作。第一级连续送 A、B、C，第二级被阻塞；第一级寄存器从 A 覆盖为 B、再覆盖为 C，而第二级仍保持旧项。没有任何错误仿真语法，但 A、B 已丢失。正确策略是让每一级使用同一套局部握手 stage_fire = valid_q && downstream_ready，并按可用空间生成 ready；或用中心控制冻结整条管线，但要冻结所有数据、valid、标签寄存器，并定义输入端行为。

信用（credit）流控是另一种选择：接收端预先告知可容纳的项目数，发送端在信用为零时停发。它减少逐周期 ready 链路依赖，适合长距离或高频片上互连，但信用的初值、回补时机、回路延迟和复位一致性需精确设计。若延迟窗口内可有多个在途项目，credit 深度须覆盖该窗口与接收缓冲，不能用单拍 ready 的直觉替代。无论采用何种流控，必须保证“发送方认为可发送”的数量永不超过“接收方实际剩余容量”。

检查清单：接口握手定义明确；valid 停顿时数据与 sideband 稳定；每一级有明确空间判定；同拍出入逻辑无覆盖；ready 链组合深度可接受或有 skid buffer；复位/flush 处理所有有效位；已握手事务不可撤销；顺序、恰好一次和标签对齐可验证；吞吐、首结果延迟和反压延迟分别记录。练习：两级管线的第二级满且 out_ready=0，一级满且新输入 valid=1，应如何响应？答案：若没有可用额外项，一级 in_ready=0，上游保持该输入；一级和二级数据均保持。若设计额外一项 skid 存储，则可接受一项，但必须证明深度确实含有这笔空间。练习二：一个 item 的数据与 tag 同拍推进但 overflow 标志只在原输入路径组合计算，为什么可能错位？答案：计算延迟和寄存级数不一致，标志可能描述相邻事务；应作为 item 同步通过同样的有效级。

第16章 FIFO 与存储接口：指针、计数、容量和碰撞语义

FIFO 把先入先出顺序抽象成写端和读端。同步单时钟 FIFO 的核心状态是存储阵列、读指针、写指针、占用计数；空条件为 count=0，满条件为 count=DEPTH。指针自然二进制回绕仅适用于 DEPTH 为 2 的幂。若参数允许非 2 幂，必须显式在 DEPTH-1 回到 0；否则三位指针用于深度 6 时会访问地址 6、7，越界，计数与实际存储也会脱节。DEPTH=1 是独立边界：地址宽应至少 1 位，读写指针没有可观察的多地址序列，满空判定仍由占用计数负责。

本章 FIFO 契约固定为单时钟、同步写、组合首字可见读：dout=mem[rd_ptr]，只在 !empty 时有效；空态没有输入到输出的直通旁路，因此空态同拍读写只写入、不读出。读请求只在非空时接受。写请求只在非满时接受；满态即使同拍读出也不接受该拍写入。若端口用 ready/valid 表达，满态 in_ready=0，源端未完成握手，必须保持 valid 和数据并重试，不能把这称为已接收或要求源端丢弃。该规则使满态读写同拍仅消费旧队首；若需无气泡“满态出入同时接受”，需把写接受条件定义为 wr_en && (!full || rd_fire) 并仔细处理同地址读写的数据碰撞与指针更新。

localparam int AW = (DEPTH <= 1) ? 1 : $clog2(DEPTH);
logic [WIDTH-1:0] mem [0:DEPTH-1];
logic [AW-1:0] wr_ptr_q, rd_ptr_q;
logic [$clog2(DEPTH+1)-1:0] count_q; // DEPTH>=1 时再封装成至少 1 位
logic wr_fire, rd_fire;
assign full  = (count_q == DEPTH);
assign empty = (count_q == 0);
assign wr_fire = wr_en && !full;
assign rd_fire = rd_en && !empty;
assign dout = mem[rd_ptr_q];

function automatic logic [AW-1:0] bump(input logic [AW-1:0] p);
  if (p == AW'(DEPTH-1)) bump = '0;
  else                  bump = p + 1'b1;
endfunction

always_ff @(posedge clk) begin
  if (!rst_n) begin
    wr_ptr_q <= '0; rd_ptr_q <= '0; count_q <= '0;
  end else begin
    if (wr_fire) begin mem[wr_ptr_q] <= din; wr_ptr_q <= bump(wr_ptr_q); end
    if (rd_fire) rd_ptr_q <= bump(rd_ptr_q);
    unique case ({wr_fire, rd_fire})
      2'b10: count_q <= count_q + 1'b1;
      2'b01: count_q <= count_q - 1'b1;
      default: ;
    endcase
  end
end

这段代码的 count_q 声明展示常见写法陷阱：$clog2(DEPTH+1) 在 DEPTH=1 时等于 1，但某些参数表达式若换成 $clog2(DEPTH) 会变成 0；稳健实现应写 localparam CW = (DEPTH < 2) ? 1 : $clog2(DEPTH+1);，并用 logic [CW-1:0]。AW'(DEPTH-1) 是尺寸转换写法，目标工具对 SystemVerilog 的支持应确认；也可使用显式参数化常量函数。另需在模块参数检查中拒绝 DEPTH<1，否则数组声明和比较没有有效含义。代码未复位存储阵列，因为 count=0 时数据无效，清整块 RAM 通常不需要且可能阻止 RAM 推断；复位指针和计数已使 FIFO 逻辑为空。

状态转移表（本章的保守满态规则）：

沿前计数 wr_en rd_en wr_fire rd_fire 沿后计数
0（空） 1 1 1 0 1
中间值 1 1 1 1 不变
DEPTH（满） 1 1 0 1 DEPTH-1
0（空） 0 1 0 0 0

错误推演：DEPTH=6、AW=3，指针只靠 3 位加法自然溢出。写入六项后指针=6，后续读访问 mem[6]，地址越界；在仿真中可能是 X，在硬件中综合对越界索引的处理不可依赖。另一个错误是 count_q <= count_q + wr_fire - rd_fire; 但分别在不同分支也给 count 赋值，或者在两个独立 if 中分别做加减：同拍读写时最后一个非阻塞赋值覆盖前一个，导致计数只加或只减。应把组合事件归并成一个 case，或者算出扩展宽度的净变化，确保同拍两边抵消。

RAM 的读延迟和同地址碰撞行为依赖实现资源与综合映射。组合读阵列易表达低延迟，但大深度常无法映射到块 RAM，可能变成大量 LUT；同步读更适合许多块 RAM，却会引入至少一个周期的读响应安排。若同一地址同时读写，返回旧数据、新数据或未定义值取决于存储宏模式，不可依靠 RTL 仿真中某个工具的数组调度来假设。AMD 的嵌入式存储器文档列出不同 read-during-write 模式，Intel 也单独定义 mixed-port 模式，说明这属于目标器件配置问题。可用旁路明确“同地址读写返回新写入值”，或选择架构避免碰撞；并以目标厂商文档和综合报告确认映射。

同步 FIFO 和异步 FIFO 不可混用指针逻辑。异步 FIFO 两边时钟不同，通常用 Gray 编码指针跨域同步，以降低多位二进制指针跨域同时变化带来的不一致采样风险；满空判断和复位释放都需要 CDC 专门处理。不能把二进制指针直接过两级同步器后就称为异步 FIFO。若不熟悉 Gray 指针满判断、指针同步延迟、复位域和物理约束，优先使用经过验证的厂商 FIFO 宏或经过验证的开源实现，并遵循其复位后等待 busy 信号等接口要求。深度不是 2 的幂时异步 FIFO 的 Gray 指针构造更复杂，不要随意套用只适用于 2 的幂深度的公式。

实现取舍：计数器法直观且任意深度都可用，但 count 到 full/empty 的组合比较可能进入状态路径；额外一位环绕位的读写指针可以区分空满，适合 2 的幂深度和特定存储架构；每槽 valid 位可实现小容量高弹性队列，但占用面积较大。FIFO 的接口也要决定是否允许满态读写替换、空态旁路、读请求是否弹出、是否提供 occupancy 和 almost-full。几种设计的 full 时序、读延迟不同，不应仅凭端口同名就互换。

检查清单：DEPTH>=1；DEPTH=1、2、非 2 幂与最大深度参数均合法；读写指针显式回绕；满态同拍读写规则写明；空态同拍读写规则写明；计数同拍更新正确；存储读延迟和碰撞模式符合目标 RAM；无效数据不被消费；复位只清必要控制状态；异步 FIFO 使用 CDC 方案和目标文档。练习：DEPTH=3 时指针序列应是什么？答案：0→1→2→0→1…，不能用 2 位自然溢出的 0→1→2→3→0。练习二：按本文规则，满态 wr_en=rd_en=1 后新写数据是否入队？答案：不入队，旧队首被读走，计数减一；若希望同时替换，必须更改 wr_fire 契约并验证 RAM 同地址读写。

第17章 仲裁：公平性、优先级和资源占用时间

仲裁器决定多个请求者中谁得到共享资源。设计前要先说清资源究竟在哪个事件上被占用：若资源每周期只完成一次操作，授予可以是一拍；若授予后要等返回完成，仲裁结果必须锁存直到事务终止；若请求本身是 ready/valid 流，则被选中的请求者只在 grant 与 valid 的握手沿完成传输。只在组合逻辑里产生 winner，却让请求者在背压期间改变请求，会导致一笔事务中途换主人。公平性也要定义指标：严格优先允许低优先级永远饥饿；轮询在持续竞争时限制最大等待，但请求保持、资源占用和取消规则都影响上界。

固定优先级适用于紧急级别有明确不同的控制，如错误恢复高于后台维护。可组合生成最高优先请求：

always_comb begin
  grant = '0;
  if      (req[3]) grant[3] = 1'b1;
  else if (req[2]) grant[2] = 1'b1;
  else if (req[1]) grant[1] = 1'b1;
  else if (req[0]) grant[0] = 1'b1;
end

此示例默认 req[3] 优先且 grant 仅表示当前组合候选，不代表事务已经被接收。若 grant 一旦给出就构成对请求者的承诺，ready=0 时必须锁存 owner，不能因更高优先级的新请求到来而换人；否则需把接口明确定义为可变候选，只有 grant && ready 才提交，且请求负载须随当前候选稳定。组合优先链随着端口数增长会形成较深路径，可以用树形编码、分级仲裁或寄存仲裁结果改善时序，但加寄存会改变可见延迟。

轮询仲裁器维护一个起始优先级指针 rr_q。每次成功授予后，指针移到获胜者之后；如果只是请求存在而没有资源握手，不能推进。更关键的是，仅保持 rr_q 并不能保证 grant 稳定：等待期间若出现新的高优先候选，组合选择仍可能换 winner。若 grant 一旦展示就必须持续到接收，必须显式锁存 owner_q/grant_q，直到握手或协议允许的撤销事件，再解除锁定；锁定期间不得因新请求改变 owner。以 4 路为例，未锁定时指针为 0 扫描 0、1、2、3；指针为 2 时扫描 2、3、0、1。实际逻辑可以展开成循环扫描函数或优先编码网络，需避免综合工具无法展开的动态循环。完成事务时刻而非授予时刻更新指针，取决于资源定义：对于每拍独立数据传输，在 grant && ready 后更新；对于一笔跨多拍的非抢占事务，在完成/释放事件后更新。

锁定逻辑的结构可写成：空闲时从 req 和 rr_q 选出候选者；当候选有效时置 owner_valid_q 并锁存 owner_q；grant 在锁定期间只由 owner 产生；握手或明确定义的撤销才清 owner_valid_q，成功握手后推进 rr_q。如果接口规定 grant 只是随时可变的候选而非承诺，则可以不锁定，但请求方必须等到独立的握手事件才提交，且所有相关负载必须跟随同一个 winner。

周期推演：四个请求持续为 1，成功传输的序列应为 0、1、2、3、0…（若初始指针 0）；每个请求在持续竞争条件下最多等待 3 次其他授予。若第二个 requester 被 grant 但资源 ready=0，仲裁指针保持原值、grant 锁定为该请求者，直到握手或明确撤销。若 ready=0 时仍每拍推进指针，波形可能显示轮流 grant，所有申请者却都无法完成；若某 requester 的请求在等待时因协议允许撤销，应在锁定策略中定义撤销后如何释放，否则可永久占住 grant。

错误推演：设计将 rr_q 在 grant_valid 时递增，其中 grant_valid 只是 req 非零。下游连续 backpressure 五拍，指针每拍移动，请求者 0 的数据没有被接收，下一拍 grant 给 1，之后给 2、3；当下游恢复，仲裁器可能交付请求 1 的数据，错误地把一个尚未完成的授权换成另一个。正确事件应是 grant_fire = grant_valid && downstream_ready，或者显式锁定 owner_q 直到事务完成。

优先级仲裁和轮询仲裁可以结合：先按流量类别选高优先类，再在类内轮询；但若高优先类永远有请求，低优先类依旧会饿死。老化（等待越久优先级越高）能提供更强服务保障，却要维护等待年龄并决定饱和行为。带宽分配仲裁器（如加权轮询）按权重发放一批 grant，需决定权重单位是事务数、字节数还是占用周期；变长事务若只按事务计数，耗时长的 requester 可能占用更多实际带宽。工程规格最好以可测量服务指标描述，例如持续竞争下每个请求在 K 次仲裁成功内获得至少一次服务，而不只写“公平”。

仲裁策略还要配合死锁分析。若请求者拿着资源 A 等待资源 B，而另一路拿着 B 等 A，单个仲裁器公平并不能打破资源环路。若仲裁授予跨域传播，应检查 CDC；通常把仲裁放在资源的时钟域，跨域请求/响应通过握手或异步 FIFO传递。多个请求同拍撤销、复位、错误取消如何处理，都要定义 owner 状态的释放条件。复位直接清 owner 可能让未完成事务被遗忘，系统上游需要共同复位或具备重试/错误响应方案。

检查清单：grant 是候选还是已接受；成功事件明确；backpressure 时 owner 是否锁定；请求撤销如何释放；公平性指标和最坏等待可证明；固定优先是否容许饥饿；变长操作按何种资源成本计权；指针复位顺序定义；复位时未完成事务如何上报；仲裁路径是否进入关键时序。练习：固定优先级中 req[3] 始终为 1，req[0] 何时得到服务？答案：不会，除非系统对高优先请求有限流或设置抢占/老化，固定优先本身不提供无饥饿保证。练习二：ready=0 时是否可以推进轮询指针？答案：若 grant 是不可撤销候选就不可以；若架构允许无状态候选扫描、且 requester 保持事务直到单独握手，则需要另行证明不会丢失或错配，不能只凭“轮询更公平”决定。

第18章 CSR：寄存器映射是一份软件可见契约

控制与状态寄存器（CSR）连接软件、固件或管理处理器和硬件逻辑。地址偏移、字段位宽、访问权限、复位值、写副作用、读副作用、保留位行为、字节使能、并发更新优先级，都是外部可观察行为；改动任何一项都可能破坏软件兼容性。CSR 并不是“几个 logic 加地址 case”那么简单，因为读写事务可能有等待周期，寄存器字段可能和硬件事件同拍更新，也可能跨时钟域。

先建立表格化的寄存器定义，再生成或手工实现 RTL。举例：CTRL 在偏移 0x00，bit0 为启动写 1 脉冲，bit1 为软件中断使能；STATUS 在 0x04，bit0 为忙状态只读，bit1 为完成 sticky 标志，写 1 清除（W1C）；COUNT 在 0x08 只读。保留位读零、写忽略。总线是否按 32 位访问、是否支持 byte strobe、读数据返回延迟、未对齐地址响应错误，必须由具体 bus 协议规定。不要假设任意 CSR 总线都和 APB、AXI-Lite 一样。

写数据应使用寄存后的事务接受脉冲驱动，而不是在 write_enable 长时间为高时每拍重复触发。write_fire 对应总线完成写传输的唯一采样事件。典型的 W1C 逻辑还需确定硬件置位与软件清除同拍时谁优先。下面假设硬件事件置位优先，软件写 1 清除只在没有同拍新完成事件时生效：

always_ff @(posedge clk) begin
  if (!rst_n) begin
    done_sticky_q <= 1'b0;
    start_pulse_q <= 1'b0;
    irq_en_q      <= 1'b0;
  end else begin
    start_pulse_q <= 1'b0;
    if (write_fire && addr == CTRL_ADDR) begin
      if (wstrb[0] && wdata[0]) start_pulse_q <= 1'b1;
      if (wstrb[0]) irq_en_q <= wdata[1];
    end
    if (write_fire && addr == STATUS_ADDR && wstrb[0] && wdata[1])
      done_sticky_q <= 1'b0;
    if (engine_done)
      done_sticky_q <= 1'b1;
  end
end

非阻塞赋值遵循“同一变量同一过程里后面的有效赋值覆盖前面的有效赋值”行为，因此这里 engine_done 分支放在最后，置位优先。若把顺序反过来，软件清除优先；这并非无关紧要的代码风格，而是并发事件的硬件契约。为避免审阅者依赖赋值顺序，也可先计算 status_next，再只赋值一次。复位后 sticky=0、irq_en=0、start pulse=0，复位值应与软件手册一致。

错误推演：软件发起一次写事务，write_enable 因从设备等待而连续保持 3 拍。若 start_pulse 直接等于 write_enable && wdata[0]，启动信号会持续三拍；若下游模块把每拍高电平视为新 start，就会重复启动三次。正确实现要根据总线协议生成一个 write_fire，或只在写握手沿上更新寄存器，并将副作用做成寄存单周期脉冲。另一错误是 W1C 采用 status <= status & ~wdata; if (event) status <= status | event_mask; 但两条赋值位置不清，可能丢掉同拍事件。先定义同拍优先级并用 next-state 表达式更易审计。

字节使能会让软件单字节写入时只更新指定 lane。若 bus 支持 WSTRB，所有可写字段都要与其对应字节使能相与；若不支持则接口需固定全字写。对 W1C 位来说，未选中的字节不能清状态。保留位常见约定为写忽略读零，但某些标准定义保留位写回原值或必须写零，需按平台手册决定。读清状态（read-to-clear）副作用会让调试器、轮询软件和非侵入性观察相互影响，应尽量避免；如必须采用，定义清除发生在请求接收还是响应交付，避免响应因等待而重复清除。

寄存器宽度跨时钟域时，不能逐位对多位总线使用双触发器同步并假设数据原子一致；不同 bit 可能在不同时间稳定，出现撕裂值。对于静态配置，可采用源端保持数据、同步 toggle 握手、目的端捕获完整总线；对于事件流使用异步 FIFO。对于硬件状态跨域回读，采用返回握手或在目的域生成镜像。硬件和软件同时改写同一字段时，定义哪个值优先、是否采用 set/clear alias、是否写一清零。CSR 的软件可见原子性也涉及 64 位寄存器在 32 位总线上的拆分读写，需要 shadow/latch 或软件高低顺序约定。

CSR 代码适合从一份寄存器描述源生成 C 头文件、文档和 RTL，但生成链也需版本控制和审查。若手写，确保地址译码默认响应有定义，未映射地址不会意外读出上次数据；不要让 rdata 在没有读请求时组合依赖浮动地址而形成外部侧信道或功耗问题。同步读常需一拍响应，接口必须允许 wait/ready；异步组合读会增加地址到数据的组合路径。读写同时对同地址发生时，规定读回旧值还是新值。对外部可观察的寄存器变更通常需要版本和兼容性评审。

检查清单：地址偏移、访问权限和复位值与文档逐位一致；byte strobe 正确；副作用仅在握手沿发生一次；W1C、读清、硬件事件同拍优先级明确；非法地址响应定义；读延迟定义；宽寄存器跨时钟域/总线宽度处理原子性；保留位行为明确；软件头文件和 RTL 的单一真源策略可追踪。练习：状态位在本拍由 0 收到硬件事件置 1，同时软件 W1C 写 1，本文规定结果是什么？答案：1，因为硬件置位优先；写清除不会吞掉新事件。练习二：CPU 写事务等待时，start 信号保持三拍是否安全？答案：一般不安全；将 bus 写事务完成事件变成单周期脉冲，并确保下游也按脉冲接受。

第19章 事务管理：命令、标签、响应和取消边界

事务管理器负责把命令送入执行资源、追踪未完成请求、把响应匹配回发起者，并处理乱序、超时、取消、复位和错误。简单的控制 FSM 往往假设“发出请求后等一个结果”，但一旦允许多个 outstanding 请求，状态就不再只是一条线，而是一张带标签的资源表。每个已接受请求占用一个槽位，直到对应响应被消费或明确终止；槽位数量、标签空间、重复 ID 规则和乱序映射都是协议的一部分。

接受请求的唯一事件是 cmd_valid && cmd_ready。在该沿为请求分配 tag/slot，锁存命令字段，并令该槽进入 PENDING。发给执行单元的请求可能再次有 ready/valid 握手；只有那个握手发生后，管理器才能把槽标成 SENT。响应回来时使用 tag 找到槽，检查它确实有效且仍在等待，锁存结果并把槽转为 DONE。对上游提供响应时，只有 rsp_valid && rsp_ready 释放槽。若内部执行响应可乱序，不能用单一先进先出响应队列强行按请求序号匹配，除非协议确实保证响应顺序。

一个事务槽至少需要 valid/状态、tag、目的端/源端标识、写入数据或结果存储、错误状态、超时计数（若支持超时）。有些字段可通过外部命令保持到完成而不落寄存，但必须考虑源端何时能撤销。slot allocation 和 free 同拍发生时，容量应允许无气泡替换还是采用保守空一拍规则；这与 FIFO 满态策略类似，需要写清。若响应能够与新命令在同一时钟沿返回，必须定义 slot tag 的复用时机，避免同 tag 旧响应误命中新事务。

错误推演：管理器以 pending_count 判断是否有未完成请求，以最近一次 tag 保存响应目的地。它允许同时接受请求 A、B，A 的请求被发出后，最近 tag 已变成 B；若 A 先响应，系统把 A 的数据送给 B 的发起者。问题不是执行单元乱序本身，而是缺少每事务独立映射。正确做法是在被接受时为每笔事务分配唯一 slot，按响应标签查表，并只在响应握手后释放该 slot。若下游只回固定顺序响应，可以用 FIFO保存映射，但协议顺序保证必须来自下游契约而非经验。

事务状态机要处理终止竞争。若响应和 timeout 同拍，哪者优先？可选策略：响应优先，避免丢掉及时到达结果；超时优先，把此事务定为失败并忽略晚响应；或者报告竞态错误并保留诊断信息。若取消与响应同拍也类似。任意选一种都会影响系统行为，写入接口文档并使软件可观察。若超时后释放 tag，而下游允许晚响应，就不能立即复用同 tag，除非响应有 epoch/generation 区分或下游在取消时保证清空；否则旧响应会被误认为新事务。常用策略是墓碑槽（tombstone）保留到晚响应抵达、generation tag、复位整个下游事务域，或协议级取消确认。有限位数的 generation 也会回绕，因此仍需限定迟到响应的最长生存时间、回绕前的复用间隔，或取得清空确认；增加一位代际并不能无条件消除陈旧响应风险。

跨模块交接要区分“已被本模块接受”和“已被执行端接受”。本模块如果在 cmd_fire 后就向上游承诺负责，则必须在内部保存完整命令，不能只保存 tag 而依赖源端保持数据。下游若阻塞，槽位仍占用并能回压新请求；发送 valid 在 ready 低时保持数据和 tag。响应数据也必须保持至上游握手。若内部单个执行单元非抢占，调度策略会影响延迟；若多个目标并行，标签空间和完成顺序管理要覆盖所有子通道。

资源规模必须有上界。槽数为 O 时至少需要 ceil(log2(O)) 位 slot index，但 tag 可能包含 generation 位；若 O=1，索引位宽仍需至少 1 位。占用位图可快速找到空槽，但优先编码较深；自由槽 FIFO 可以提高分配时序，但复位和并发分配/释放更复杂。响应 CAM 按外部 tag 查表可并行但面积随 O 增长。对小 O，显式 case 可能最清楚；对大 O，存储映射或 bank 化要查看综合后结构。不要为节省几十个寄存器而引入不可审计的 tag 复用假设。

检查清单：请求接受点与槽分配点一致；完整负载被保存；槽在所有终止路径恰好释放一次；并发响应可正确匹配；下游停顿期间请求稳定；上游停顿期间响应稳定；ID 唯一性和复用约束明确；超时/取消后的迟到响应策略明确；同拍分配释放容量行为明确；复位时未完成事务如何响应上游；计数器不会在重复完成时下溢。练习：容量 2，槽0和槽1都有效，槽0本拍响应握手，同时新命令到达，能否同拍接受？答案：能否由接口契约定义；若允许，应保证分配逻辑可复用本拍释放的槽，并确保迟到信号不会把旧槽误释放。如果实现保守拒绝，新命令需保持 valid 至下次 ready。练习二：超时后立即复用原 tag，但旧响应可能晚到，风险是什么？答案：旧响应会匹配新事务；需延迟复用、增加代际标识或得到取消确认。

第20章 错误、超时与恢复：设计可控的故障路径

故障处理不能只写“超时则报错”。需要明确检测条件、故障分类、恢复动作、对外响应、重试策略和故障期间资源占用。常见故障包括响应超时、校验失败、非法状态、FIFO 溢出/下溢、总线返回错误、目标复位、CDC 链路失效以及软件取消。每类故障都需要判定是否可恢复、是否可能重复执行副作用，以及怎样避免一笔请求永远挂住。工业模块的正常路径可能简单，故障路径却决定系统能否在部分组件异常时继续工作。

超时通常由事务管理器按“等待响应”状态计数。应规定计时起点：命令被本模块接受时，还是下游真正接受时。若下游背压很久，把等待响应时间从上游接受沿开始计，会把拥塞误报为目标无响应；若目标迟迟不接受请求，则这是发送/排队超时，可能需要另一计时器。计数到期的边界同样要走周期表。例如 limit=5，从下游接受沿之后的五个采样沿没有响应才超时，计时器应与第13章的 N 个后续沿定义一致。若响应与超时同拍，优先规则明确且能在 RTL 中表达。

always_ff @(posedge clk) begin
  if (!rst_n) begin
    wait_q <= 1'b0;
    age_q <= '0;
    timeout_q <= 1'b0;
  end else begin
    timeout_q <= 1'b0;
      if (request_fire) begin // 仅空闲时接受；本例不支持零周期响应
      wait_q <= 1'b1;
      age_q <= '0;
    end else if (wait_q) begin
      if (response_fire) begin // 等待态下响应优先于超时
        wait_q <= 1'b0;
        age_q <= '0;
      end else if (age_q == LIMIT-1) begin
        wait_q <= 1'b0;
        age_q <= '0;
        timeout_q <= 1'b1;
      end else begin
        age_q <= age_q + 1'b1;
      end
    end
  end
end

此片段仅表达单笔等待，省略位宽保护、零限值策略和事务槽。LIMIT=0 时 LIMIT-1 会下溢或得到宽度不符常量；应参数检查要求 LIMIT>=1，或把 0 定义成关闭超时。契约要求 request_fire 只在 wait_q==0 的空闲态产生，且本单笔版本假定请求至少隔一个采样沿才可能收到响应，不支持接受请求的同沿零周期响应。代码的外层 if (request_fire) ... else if (wait_q) 意味着若错误地让 request_fire 与 response_fire 同时为 1，请求分支优先；在该契约下这种组合不应发生。若总线确实允许零周期响应，必须加入接受沿旁路/同拍完成逻辑，并重新定义请求、响应和超时优先级。更复杂的事务管理器应在每个 slot 上维护独立年龄或共享扫描计时器，不可让一笔响应重置所有其他事务的计时器。

错误推演：请求在时钟沿被接受并令 age=0。若代码每拍先加一，随后用 if (age==LIMIT) 判断，非阻塞赋值读的是旧值，超时会在预期之外晚一拍；若启动沿也被计入，则又可能早一拍。把 limit=1 手工展开：接受沿后 age=0；第一个后续沿若无响应，应产生 timeout=1。用这个最小边界验证实现。另一个错误是 timeout = wait && age==LIMIT 作为组合输出而没有寄存脉冲，状态清除/优先级改变时它可能在周期边界持续两拍或被外部漏采。

错误恢复有不同级别。局部重试适合幂等操作；若写寄存器、发射中断或扣减资源的事务可能已经在目标端执行，超时并不意味着“没发生”，盲目重试可能重复副作用。要么事务带唯一 ID、目标支持去重，要么读回确认，要么把操作设计成幂等，要么把结果报为“不确定”交由上层决策。局部软复位可以清理状态但会丢弃内部待处理事务；系统级复位影响面更大，也可能让未完成写入处于未知状态。复位策略应描述对未完成请求是否返回错误、是否要求上游复位、是否等待下游 reset-busy 解除。

故障锁存和恢复命令需保护诊断信息。可以记录首次错误码、事务 tag、目标地址、时间戳或累计计数；规定首次错误保持还是最新错误覆盖，以及软件清除和新错误同拍时优先级。错误信号应避免直接跨域；sticky 状态跨域也应通过同步或握手读取。安全输出在故障态应进入已定义值，例如关闭写使能、停止发送新请求、保留响应通道可回错误，不能让错误状态导致 valid 永久高且 data 未定义。若错误路径使用多周期清理状态机，应确保对外背压和资源释放有界。

检查清单：每个故障有检测、记录、响应、恢复策略；超时起点和边界定义；响应/超时同拍优先级明确；limit=0 和最大 limit 有定义；重试仅用于安全可重复操作或具备去重；超时后 late response 和 tag 复用有方案；复位/取消对未完成事务的结果已定义；安全输出在故障态已约束；故障记录的清除优先级明确；计数器按事务独立而非误影响其他 slot。练习：非幂等写命令等待超时后，是否应该自动重发？答案：不能默认重发，因为目标可能已经执行，只是响应丢失；需由协议去重、读回判定或上层确认。练习二：LIMIT=1，命令接受沿后第一个沿无响应，本文示例应何时 timeout？答案：该第一个后续沿，age_q 沿前为 0，比较 LIMIT-1 命中并产生单周期 timeout。

第四篇　时序、功耗与系统可靠性

第21章　时钟、复位与使能控制

21.1 时钟定义状态变化边界

时钟不是普通的一位信号。它规定状态何时采样输入、何时更新输出，并由时钟树、静态时序分析和域分析共同解释。每个时钟都需要明确其与其他时钟的关系：同源且相位关系确定的时钟可作为相关同步时钟分析，异源或相位不确定的时钟则需按异步域处理；新时钟会增加时序关系与分析责任。用组合逻辑产生时钟，或让普通数据路径信号直接驱动 posedge，会使时序工具难以识别时钟拓扑，也可能产生窄脉冲、重复边沿或不可控偏斜。ASIC 时钟门控应使用经验证的集成时钟门控单元（ICG）；FPGA 通常应优先使用专用时钟使能或时钟缓冲资源。具体做法由工艺库及器件架构决定。

很多“省电门控”可以用寄存器使能描述：

always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n) q <= '0;
    else if (ce) q <= d;
end

这表示复位优先、使能有效时更新、否则保持。硬件可能是带使能触发器，也可能是输入多路器加触发器；源码不承诺具体映射。ce 必须满足该时钟域的采样契约；若来自异步域，应先同步单比特电平或使用握手，不能以“脉冲够宽”作为隐含假设。全局高扇出使能会增加布线负载和时序压力。它是否比专用门控省电，须按目标平台测量功耗、面积和时序。

21.2 复位策略是接口契约

同步复位只在活动时钟沿采样；异步复位的断言可不等时钟沿立即影响触发器，而其释放须满足触发器 recovery/removal 要求。异步复位常用于时钟尚未稳定时快速进入已知状态，但随意释放会让不同触发器在不同周期退出复位，形成非法状态或短暂控制脉冲。常见工程结构是“异步断言、同步释放”，每个时钟域使用自己的释放同步器。

(* ASYNC_REG = "TRUE" *) logic [1:0] rst_sync;
always_ff @(posedge clk or negedge arst_n) begin
  if (!arst_n) rst_sync <= 2'b00;
  else         rst_sync <= {rst_sync[0], 1'b1};
end
assign rst_n = rst_sync[1];

这里 arst_n 低有效异步断言，rst_n 在 clk 域同步释放。属性写法要按综合、布局布线工具的识别规则确认。若复位源毛刺、脉宽不足或分发不受控，同步器不会修复复位源质量。复位网络的扇出、分区、极性、上电行为、扫描模式和 IP 要求都要纳入集成契约。

复位所有寄存器看似保守，却可能造成大复位树、面积和拥塞。有些数据寄存器可不复位，只复位 valid/占用状态，并规定无效数据不可观察。该做法只有在接口契约保证无效数据不会被消费、复位期间输出被屏蔽且相关安全属性可验证时成立。权限、地址、安全状态和控制信号要更慎重。

21.3 交互失效推演

假设 FSM 采用异步低有效复位，valid 却采用同步复位，数据寄存器不复位。上电时异步复位立即把 FSM 清零，但 valid 可能仍为 1，直到下一个时钟沿；下游在此前读取无效数据。另一个错误是将复位放在使能分支内：if (ce) begin if (!rst_n)...，当 ce=0 时复位被屏蔽，状态不会清零。逐类寄存器明确复位优先级，并规定 reset、flush、clock enable 同时发生时的优先次序。

21.4 时钟门控、复位释放与启动契约

时钟使能不等于门控时钟。使能寄存器每个时钟沿仍由原时钟触发，只是在数据端选择保持；门控时钟改变触发事件和时钟树活动。若模块要频繁停止，架构应先决定停的是计算数据更新还是整个时钟域。后者需要门控单元、测试旁路、门控使能锁存时序、STA 时钟定义和唤醒流程。具体锁存相位由 ICG 结构决定。

一个域内多个模块若各自有释放同步器，可能在不同周期退出复位，短暂形成域内局部复位差异。可由域级 reset controller 统一生成 reset_done，或明确各模块在初始化握手完成前不得互相消费状态。复位树还须满足扇出、脉宽、恢复和移除要求；RTL 仿真的 0/1 边沿并不模拟模拟电气条件。同步复位也不是对所有触发器都免费，某些库会在数据端综合 mux 并增加路径延迟。

时钟停止期间释放复位时，同步释放电路会因没有目的时钟而保持复位；系统不能依赖它自动启动。时钟恢复后仍需等待同步级数和初始化握手。PLL lock 也可能再次失效，复位控制需定义重新失锁后的行为。

21.5 审查与练习

检查：每个时钟在约束中有定义；区分主时钟、生成时钟和门控时钟；没有组合逻辑产生时钟边沿；复位断言/释放、极性、同步级数及域归属写入接口文档；复位与使能同时有效的优先级明确；未复位数据始终被有效位屏蔽；复位后协议对在途事务的丢弃或重试行为已定义；时钟停止时复位、唤醒和状态保持仍满足系统要求。

练习：写出同步清零、使能时加一的计数器，且复位有效时使能无关。答案：在 always_ff @(posedge clk) 中先 if (clear) count <= '0; else if (ce) count <= count + 1'b1;。这是同步清零；若需求为异步断言，应改变事件控制并评估释放时序，不能只在敏感列表里加一个信号就认定设计完成。

第22章　跨时钟域与跨复位域设计

22.1 CDC 不只是“延迟两拍”

发送端和接收端没有固定相位关系时，接收触发器可能在数据变化附近采样而进入亚稳态。亚稳态具有模拟连续性，RTL 四态仿真不能模拟它的电压和解析时间。两级或多级同步器给第一级更多时间在数据传至后级前稳定，从而降低亚稳态传播概率；它不把概率降为零，也不保证源数据语义正确。MTBF 依赖器件参数、时钟频率、数据翻转率、解析时间、布局和负载，应使用器件模型或工具估算，不能把“两级”说成绝对安全。

(* ASYNC_REG = "TRUE" *) logic sync1, sync2;
always_ff @(posedge dst_clk or negedge dst_rst_n) begin
  if (!dst_rst_n) begin sync1 <= 1'b0; sync2 <= 1'b0; end
  else begin sync1 <= async_in; sync2 <= sync1; end
end
assign dst_level = sync2;

这只适用于允许目的域观察延迟后单比特电平的场景。若源脉冲窄于目的时钟采样间隔，可能完全漏采；每个事件都必须送达时，采用脉冲拉伸、toggle 同步、req/ack 握手或异步 FIFO，按吞吐与反压要求选择。多位总线逐位加两级触发器是错误方案：不同位可能在不同目的周期更新，接收端会看到从未存在过的混合字。

22.2 握手、Gray 总线与异步 FIFO

低吞吐配置字可用握手：源端锁存数据并保持到收到确认；同步 req 到目的域，目的域采样稳定数据并回 ack；ack 同步回源后，源端才能更改数据。数据总线由握手提供稳定窗口，不是逐位独立同步。协议须定义复位时 req/ack 初值、复位打断时事务是否作废、两端独立重启如何避免旧 req 被当成新事务。稳定窗口须覆盖路径延迟和目的端采样要求，仍需约束及 CDC/物理检查。

高吞吐使用异步 FIFO：双口存储器由各自时钟读写，二进制指针在本域递增，Gray 编码指针跨域同步，目的域据同步指针计算 full/empty。Gray 相邻计数只变化一位，降低同时变化产生的混合风险；但 Gray 编码不能消除物理布线偏斜。若各 bit 延迟差过大，前一计数的慢位与下一计数的快位可能同时到达，接收器看到多个位变化，破坏“一次只变一位”前提。因此对 Gray 总线施加符合设计目标的最大延迟或总线偏斜约束，并检查覆盖与实现路径。同步链按目标器件推荐方式识别和布局。

function automatic logic [PTR_W-1:0] bin2gray(logic [PTR_W-1:0] b);
  return (b >> 1) ^ b;
endfunction

FIFO 的 empty/full 判定、指针位宽、二次幂深度前提、跨域复位和读写同周期边界都易错。应采用经验证的标准结构或器件 FIFO IP，不要只凭口诀改写最高位比较。full/empty 是各自时钟域里的保守状态指示，更新带同步延迟，并非即时全局事实。

22.3 异步 FIFO 的复位契约

复位必须定义两域是否共同置位、复位期间是否禁止读写、指针同步器初值、输出数据有效性和释放后何时恢复操作。若写域复位而读域继续运行，读域可能持有旧同步指针并对 FIFO 内容作出不一致判断；单边复位也可能让双方对队列认知不同。可以采用系统级共同复位并在解除后等待同步链稳定，也可设计明确的 flush/epoch 协议；两级同步器不会自动修复任意独立复位。

阶段 写域 读域 操作
任一复位断言 清写指针/同步链 清读指针/同步链 禁止读写，输出无效
释放第1拍 本地复位仍有效 本地复位仍有效 禁止

若两域启动时间不同，应使用跨域初始化握手，而不是凭固定延迟猜测对端已醒。

22.4 亚稳概率、编码前提与 CDC 例外

设源端每拍翻转状态位，目的端两级同步。第一拍可能因 setup/hold 窗口进入亚稳，经过一个周期仍有极小概率未解析，第二级便可能采到不确定电平。增加级数、降低目的频率或源翻转率、改善同步器布局都可提升 MTBF，但不会形成零故障保证。多条同步链的整体失效率要考虑各链累积，不能只报告最好的一条。两级之间插入组合逻辑、扇出负载或长布线会削弱解析时间；保护属性须按实际工具识别规则设置。

再看总线故障：二进制计数从 0111 到 1000 时四位同时改变；目的端可能采到任意混合码。每位单独同步也无法保证一致性。Gray 码只对相邻变化约束单 bit；若源端可以跳过多个计数值，Gray 总线也不再有相邻只变一位的性质。因此其前提包括源端以单位步长单调递增或递减。任意跳变状态应使用握手或安全编码。

CDC waiver 证据应包含源/目的时钟关系、协议、观察方式、物理约束、复位条件、工具识别结构及责任人。“总线稳定”须说明谁锁存、何时改变、目的端在哪个窗口采样，单纯注释不能替代协议。

22.5 RDC、检查与练习

Reset Domain Crossing（RDC）关注不同复位域的状态交互。同一时钟而复位释放不同步，仍可能有异步控制或部分复位状态传播。分析复位源关联、异步断言、同步释放、复位树、隔离/保持策略和复位后协议。CDC 工具能发现结构风险，但豁免需附结构图、协议说明和复核记录，不能凭“仿真没错”免责。

检查：按电平/脉冲语义分类单比特 CDC；每个多位总线有握手、Gray 或 FIFO 协议；源端保持及接收采样点清楚；同步器无组合逻辑插入并受工具识别；脉冲可能漏、重、合并的情况有分析；Gray 总线物理偏斜约束已覆盖并检查；异步 FIFO 深度、指针来自已审查模板；复位单边/同时发生、时钟暂停和重启已定义；CDC/RDC 例外可追溯。

练习：目的时钟 100 MHz，源端每 20 ns 产生宽 2 ns 脉冲，要求每个事件被目的端处理。两级同步器足够吗？答案：不够，脉冲可能完全落在采样间隔内而漏掉。采用源端 toggle 编码加目的域同步和边沿检测，或 req/ack 握手。单纯 toggle 只有在每次翻转都能被目的域观察、且两次翻转之间有足够最小间隔时才不丢事件；若没有可证明的速率上界，就必须等待目的域反馈 ack 后再翻转。还要定义复位时双方 toggle 的对齐规则。

第23章　面向时序收敛的 RTL 设计

23.1 RTL 与约束共同定义时序问题

RTL 描述功能关系，STA 在时钟、输入输出延迟、时钟不确定度、例外路径和库时序弧上检查实现。寄存器到寄存器 setup 预算粗略包括周期、捕获相对发射的有利偏斜，并扣除 setup、时钟不确定度和数据最大延迟。hold 则关注最小数据延迟、保持时间和时钟偏斜。具体符号以时序报告与库模型为准。仅数逻辑级数不够：长线、高扇出、拥塞、时钟偏斜也能使路径恶化。

优化从最差路径和端点入手：串行算术链、优先级 mux、比较树、控制扇出还是跨层连接？重写前先判断功能是否允许改变延迟、吞吐和资源。把 a+b+c+d 写成平衡树，须确保位宽、符号扩展、截断和饱和规则一致；流水化能缩短单周期组合路径，却增加延迟、寄存器面积、时钟功耗和 valid 对齐责任。

always_comb begin
  sum0 = a + b;
  sum1 = c + d;
  sum  = sum0 + sum1;
end

平衡形式不保证映射一定更快，综合器可能已重构。应记录前后约束、工具版本、综合/实现设置、面积、WNS/TNS、功耗和等价性证据，最终复核布局布线结果。

23.2 结构选择与常见失败

高位宽比较、优先编码器可能导致逻辑深度和高扇出；加入寄存器虽可切段，却引入延迟，须由接口协议接受。状态译码若一个状态位扇出过高，可考虑局部寄存、层次化译码或复制控制；副本的复位、使能、更新条件必须一致。组合环路、锁存器推断和过长组合依赖链都是收敛风险。层次模块过度拆分也可能妨碍优化或增加布线，应兼顾验证、复用与物理布局。

多周期例外是对功能时序的声明，不是修复坏路径的捷径。若路径两端每 N 周期才更新，必须证明启动/捕获关系、使能相位和异常条件确实让数据有 N 周期；只把约束设为 N 周期，可能掩盖每拍变化的数据丢失。异步 CDC 路径不能按同步 setup 关系进行安全同步验证；可以不按普通同步路径定时，但 Gray bus 的最大延迟/偏斜仍需约束。同步时钟错误设置 false path 会让真违例从报告消失。

23.3 流水线周期推演

边沿 第1级 第2级输出 valid
n 采入 A、B，算部分和 前一事务结果 valid[n-1]
n+1 采入 C、D，算新部分和 事务 n 结果 valid[n]

常见缺陷是数据加了寄存器，valid、tag、exception 或 sideband 没同样延迟，结果与标志错配。背压时还要决定寄存器冻结、弹性缓冲和允许覆盖条件。延迟、启动间隔 II 和吞吐是不同指标，评审须分别核对。

23.4 约束误用与物理修复

时序异常可能来自路径，也可能来自约束错误。输入延迟漏设会让输入到寄存器路径看起来比现实宽松；生成时钟没定义会使路径未约束；过宽 false path 会屏蔽真实关系。先检查 unconstrained path 和时钟交互报告，确认时序引擎理解的关系与架构一致，再解释 slack。修改约束前画出发射沿、捕获沿及接口时序，不能以调到变绿为目标。

修 setup 可能加入流水寄存器，但还需检查 hold。逻辑重构缩短最小数据延迟时可能增加 hold 违例；后端插 delay cell 会增加面积、功耗和拥塞，严重时影响 setup。不能用无功能意义的 RTL 延迟修 hold，应由正确约束和实现流程处理。复制局部寄存器可降低高扇出，却增加面积和一致性证明责任；副本须对 reset、scan、enable 一致，跨域分叉还会形成新的 CDC。每次优化后检查新路径、资源和协议副作用。

23.5 STA 闭环、检查和练习

先检查约束完整：时钟波形、生成时钟、输入输出延迟、时钟不确定度、异步时钟关系、例外路径。再按报告确认最差 setup/hold 路径，查看发射与捕获时钟、cell/net 延迟、扇出、层级和物理位置。改动后跑完整综合和实现，检查 setup、hold、设计规则、时钟报告；不能因 WNS 转正就忽略其他时钟域 TNS、hold 或未约束路径。综合估算线延迟不能替代实现后 STA。

检查：知道频率和延迟预算；检查未约束端点；能解释最差路径；保留吞吐/延迟契约；多周期/false path 逐端点复核；流水 sideband 对齐；实现后 setup/hold 闭合；优化前后等价证据和 PPA 配置可追溯。

练习：慢路径由 32 位累加、饱和比较和选择器组成，能否声明 multicycle 2？答案：只有设计保证输入/状态至少两拍稳定、捕获寄存器确实按该关系采样、协议允许延迟，并由属性和约束共同证明时才能。否则应优化组合结构、流水化或重新分配周期，不能用约束掩盖一拍功能义务。

第24章　面向功耗与面积的 RTL 设计

24.1 PPA 是约束，不是代码竞赛

面积取决于状态位、组合逻辑、缓冲、时钟/复位网络、存储器和物理修复；功耗包含动态、短路和漏电。动态功耗通常随有效电容、活动率、电压平方和频率增加。RTL 可影响活动率与结构，但真实功耗受器件、工艺、电压、时钟树、布局布线和输入活动驱动。面积减少不自动降低功耗：较小逻辑若造成更高扇出或更长导线，动态能耗可能上升；共享算术单元省重复面积，却可能增加 mux、控制切换、关键路径和活动率。

先定义优化目标与测量口径：综合面积还是布局后面积，峰值还是平均功耗，工作模式和输入活动来自真实 trace 还是假定 toggle rate。缺少同一约束和活动输入，A/B 数据不可比较。结构分析提出的是假设，不能冒充实测结论。

24.2 切换抑制与结构权衡

若状态在 ce=0 时必须保持，条件更新可以避免寄存器改变：

always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) q <= '0;
  else if (ce) q <= next_q;

这可能推断寄存器使能，也可能映射成 mux；是否降低功耗取决于目标单元。若 next_q 在 ce=0 仍不断翻转，寄存器不更新但前级组合仍耗电。可考虑 operand isolation，但不能在时钟敏感路径制造毛刺。组合 AND 时钟若使能在时钟高电平期间变化，会截断或制造时钟脉冲，不能替代合格时钟门控。

两路互斥操作共享一个加法器可减面积，但引入输入 mux 和选择控制延迟；复制运算器可能面积高却时序好。状态编码也类似：二进制用较少触发器但译码复杂，one-hot 用更多触发器但可能降低译码深度。没有脱离目标库、频率和活动模式的“总是最省”选项。

24.3 面积优化可能改变功能

缩窄计数器、减小 FIFO 深度或移除寄存器会减少面积，也可能改变规格。地址宽从 16 缩成 12，须证明上层不会访问被裁掉空间；无符号加法截断会模回绕，若需求饱和就不等价。共享状态也可能降低并发能力；两个请求可同时到达时，串行化会造成吞吐下降或死锁。面积账本应包括时钟树和可测性电路，而非只看 RTL 行数。

24.4 活动率分析与可复现比较

功耗优化要区分时钟活动与数据活动。宽寄存器即使保持不变仍可能随时钟树消耗功耗；门控可降低该部分，但门控单元、时钟树重平衡和测试旁路也有代价。输入随机跳变时，操作数隔离可能减少组合毛刺；若输入本来很少变化，额外 mux 反而增加面积和路径。应从功耗报告定位高活动、高电容实例，不把“总线很宽”直接等同“功耗一定高”。

对照两版的活动文件须来自相同工作负载和窗口；复位启动瞬态是否纳入，两版必须一致。没有真实活动数据时，工具默认活动率只是估算假设，不能称为测量。比较还需统一电压、频率、约束、库角和物理配置。差异小于估算误差时应报告不确定性。常见优化失败是只给结果寄存器加 enable，却未对齐 valid、tag 和异常标志；数值正确但事务标签错位。另一失败是组合门控时钟在仿真偶然正常，芯片上因毛刺多出边沿。优化先守住契约，测量后才能称为改进。

24.5 低功耗状态与唤醒

关时钟或电源会改变状态可观察性，须定义休眠安全点、在途事务完成/取消、输出隔离、保持寄存器、唤醒源及稳定等待期。RTL 可暴露 idle、quiescent、wake_pending 状态，但不能独立实现电源完整性；电源意图、隔离和 retention 由系统低功耗流程定义，RTL 与电源控制必须对齐。若唤醒脉冲来自停钟域，应由常开域保持或握手；脉冲不会因“接了同步器”而在时钟停摆时自动被捕获。

检查：目标和测量窗口明确；活动率来自代表场景；功耗类型区分；目标平台支持时钟使能；门控组合是否仍切换已检查；共享单元的路径/吞吐已核算；面积优化没改变地址/并发/错误行为；低功耗恢复有契约；优化经过等价/功能验证且配置一致。

练习：合并两路互斥加法器一定省电吗？答案：不一定。虽减少加法器电容，却增加选择器、控制切换和可能更长路径，输入活动率也可能上升。须以相同工艺、约束、工作场景、活动 trace 对照实现，并确认延迟与吞吐。

第25章　面向集成、测试与可观测性的设计

25.1 契约让 IP 可集成

IP 功能不只包含内部状态转移，也包括参数合法范围、时钟与复位要求、输入输出稳定条件、错误响应、背压行为、中断清除语义和未定义配置处理。接口文档应说明每个输入的采样域、输出有效条件、复位值和复位中断事务的后果。模块在子系统里会连接不同速率总线、复位源和时钟门控策略；假设若不写明，顶层只能从波形猜。

参数宏应在 elaboration 阶段给出明确诊断。非法宽度用静态断言或错误报告，不要依赖零宽数组或截断偶然编译失败。默认配置应可安全集成。总线在 valid=0 时数据是否任意，由契约决定；若安全或功耗要求保持/清零，需接受相应 mux 和活动成本。

25.2 可观测点应有诊断价值

可观测性是从外部症状定位内部事件的能力。可提供计数器、sticky error、状态摘要、超时原因、队列水位和性能事件，但每个诊断寄存器增加面积、时钟/复位负载及 CSR 行为。计数器定义饱和/回绕、读清/写清、并发读写优先级和复位值。错误记录需防止后续无关错误覆盖先发关键信息；必要时用 first-error latch、错误向量或时间戳。观察点宜围绕诊断事件，避免将实现细节变成软件依赖。

异步读取内部计数器可能读到撕裂值；可通过快照握手、Gray 码或源域冻结。直接把二进制状态总线接到 CSR 域是不安全的。对内部不可见状态可使用 bind checker 或正式调试接口；调试接口也有时钟域、权限、稳定读数和扫描模式契约。

25.3 DFT 与功能 RTL 的交界

DFT 不只是后端插入扫描链。RTL 设计者应识别影响测试的结构：异步复位在测试模式是否可控；时钟门控有无测试使能；状态和存储器的可控性/可观测性；低功耗隔离是否阻断扫描；不可扫描或黑盒 IP 如何测试。测试模式 override 要有明确优先级，防止功能态误触发。扫描架构、ATPG 覆盖率和压缩由 DFT 团队决定，RTL 接口须匹配，普通功能仿真通过不等于可测。

失效推演：门控时钟由 clk & en 组合产生，功能仿真中 en 恰在时钟低电平改变，波形看起来正常；扫描期间 en 在高电平变化，门控输出多出窄脉冲，移位状态错乱。应采用经认可且含测试使能的 ICG，并检查门控时钟检查和 DFT 插入后的时钟路径。另一个故障是复位脉冲过窄，同步复位触发器从未采样到，芯片上电状态随机；需规定复位源脉宽或采用异步断言结构。

25.4 顶层集成失效链

假设子模块的 done 是仅持续一拍的脉冲，顶层连接到低频控制域；无固定相位时脉冲可能漏采。单模块仿真中两个时钟同源同相，问题不现身。接口须标注脉冲所属域及交付保证；若顶层要求可靠事件，应使用握手或 toggle，不能期待集成方自行拉宽。端口名也不能表达复位断言和释放契约；模块间复位错开时，彼此观察状态仍可能失败。

CSR 文档同样是集成契约。读清寄存器在同周期有新事件时，是返回旧值后清除还是保留新事件？软件通过总线等待期间，源域状态可能变化，需要快照和 CDC。电平中断在清除后条件仍成立会重新置位；脉冲中断则可能被软件错过。将这些时序定义写入寄存器说明，并由 RTL checker 对照，能减少“写 1 清除”的歧义。集成前还应核对地址译码默认响应、未映射访问、权限错误、总线超时和跨复位域状态一致性。

25.5 检查与练习

接口检查：每个信号注明方向、时钟域、有效/稳定、背压和复位行为；参数范围、默认值和非法配置报错明确；未用输入不悬空。诊断检查：每个状态有读写语义、时钟域和资源成本；并发事件优先级明确；权限边界清楚。DFT 协作：门控时钟有测试使能；异步复位在测试场景受控；存储器/黑盒有测试方案；隔离、扫描、时钟和复位联合检查。

练习：设计跨两个域的 16 位错误计数器读取口。答案：读请求触发源域锁存快照并用握手传递，源域保持快照直到确认；接收域再读取稳定值。若需持续计数且精确快照，由源域专门生成快照。逐位同步 16 位二进制总线不能保证一致性。还应定义复位打断和等待超时策略。

第五篇　验证与正确性保障

第26章　可验证性设计与验证计划

26.1 从需求分解证据

验证计划把外部需求转成可判定、可重复的证据。每项需求应有标识、前置条件、刺激、期望结果、观察点、验证层级和覆盖目标。“FIFO 正常工作”不可判定；应拆为：空时读不改变指针并按契约输出无效；非空读恰好移除一项；读写并发保持数据顺序；满时写被拒绝或按合同覆盖；复位打断后旧数据不可读。再决定用仿真、断言、形式化、CDC 分析或实现后检查。

验证覆盖功能空间和时序情境。握手至少考虑单拍请求、持续 valid、任意背压、请求响应同拍、复位在各阶段发生、错误响应和超时；参数化模块覆盖最小/最大合法参数及边界。随机测试增加序列多样性，却不代替边界推演；覆盖率只描述模型记录的事件，不证明需求正确或断言无空洞。

26.2 可验证性来自结构

稳定观测边界、明确状态不变量和可控输入有利于验证。把组合决策、状态寄存器、握手状态分清，利于 checker 绑定和形式建模；为测试暴露内部信号则会增加接口耦合。可围绕模块契约检查输出，必要时在验证环境 bind 内部不变量。错误恢复设计可提供原因码和 sticky 事件，否则测试只能推测卡住原因。

ready/valid 数据通路的重要属性：valid && !ready 时数据和 sideband 保持；握手时恰好消费一项；复位优先清除未完成状态；连续 ready 时达到预期吞吐。随机输入及 scoreboard 应在 valid 与 ready 同一采样沿均为真时入队/出队，而非看到 valid 就更新。

26.3 需求映射与证据边界

需求 证据 刺激/假设 覆盖/检查
背压下数据保持 SVA + 定向仿真 ready 可任意拉低 stall 与恢复握手
FIFO 数据顺序 scoreboard + 形式属性 写读遵守接口 空满边界、并发
复位清除在途事务 仿真 + 断言 任意阶段复位 每状态复位交叉

不同证据发现不同类别缺陷。仿真可观察复杂交互；形式化可探索状态路径但依赖抽象与假设；静态分析发现结构风险但不证明功能。计划须说明证据边界，不能以“Formal 已过”替代完整工程判断。

26.4 风险优先级和证据组合

验证资源有限时，应按失效影响和可发现性排序。丢数据、越权访问、死锁、复位后错误状态通常高于非关键诊断计数偏差。风险表可记录严重度、概率估计、检测手段、残余风险和责任人；它不是精确数学，而是解释投入优先级并暴露未证明假设。

每条关键需求最好有独立于实现的 oracle。参考模型若直接调用 DUT 组合函数，二者可能共享同一错误。可写简单独立模型，或检查守恒、范围、事务顺序等属性。仿真验证具体轨迹，形式化检查所建模状态空间内的不变量，二者互补；若形式假设排除了回归场景，应审查产品边界。复位覆盖应交叉到空闲、等待响应、背压和错误恢复等协议阶段；只覆盖 reset 拉低事件不能说明其对每种状态的作用。覆盖洞要区分不可达、未生成、未采样和被 ignore，配合断言命中一起审阅。

26.5 失败推演与退出标准

若 scoreboard 在事务发出而非握手时入队，遇到 valid=1, ready=0 就会重复记录，之后误报 DUT 多发数据。若假设 ready 永远为 1，回归永不暴露背压丢数。若只在 idle 注入 reset，复位恢复路径未覆盖。需审查 TB 自身协议正确性，并记录随机 seed、软件版本、约束和失败重现步骤。

退出标准：需求都有证据或批准豁免；严重缺陷关闭；断言启用且失败可追溯；功能覆盖达到项目目标并解释洞；关键参数/复位/错误场景通过；lint、CDC、形式化、综合检查豁免有责任人与依据；回归可复现。门槛由项目定义，不能宣称是语言标准要求。

检查：需求可观察可判定；风险匹配验证手段；环境约束不超出产品契约；参考模型按握手事件更新；边界、并发、复位、错误、背压都列入；覆盖点追溯需求；失败可重放；形式化假设审查；门禁和退出标准明确。

练习：写“复位后 FIFO 为空”的验证思路。答案：先明确复位立即禁止输出，还是释放且完成 CDC 同步后才报告空；再在空/半满/满、读写中各阶段断言复位，检查 empty 本域语义、valid 无效、旧数据不可消费、指针归零且初始化后恢复；用 SVA 检查边沿，用 scoreboard 检查序列，并模拟两域错开释放。

第27章　SystemVerilog Assertion 设计艺术

27.1 并发断言采样语义

并发断言在触发事件时对变量取采样值，通常在时钟沿的 Preponed 区采样；随后 RTL 在 Active/NBA 等事件区执行，NBA 更新后变量当前值可能不同。断言在 Observed 区求值，所以属性里的 q 通常是该沿采样的旧值，而不是 NBA 刚写入的新值。这解释了常见的一拍错位：

assert property (@(posedge clk) en |=> q == $past(d));

它表示采样沿 en 为真，则下一采样沿 q 等于前一采样沿采样的 d，适用于无其他优先分支且更新关系符合的场景。若 clear 优先，必须把 clear 条件纳入属性。|-> 是同一采样时刻重叠蕴含；|=> 的 consequent 从下一采样时刻开始；##N 是采样事件间隔而不是绝对时间。

disable iff (reset) 用于异步中止进行中的匹配，其表达式不按普通属性表达式那样使用时钟采样值，因此 reset 可在时钟沿之间改变并影响禁用状态。它不会证明 reset 解除后的第一拍有效，也不等价于 antecedent 前的同步 reset 条件。若要求同步复位语义，或需精确处理 reset 与时钟同仿真时刻的竞争，应按 IEEE 1800 语义和工具支持明确写法，并做小型语义实验；不要把 disable iff 当成万能同步门控。

27.2 属性必须对准契约

property p_hold_while_stalled;
  @(posedge clk) disable iff (!rst_n)
    valid && !ready |=> valid && $stable({data, last});
endproperty
assert property (p_hold_while_stalled);

它表示发生一次阻塞采样后，下个采样沿 valid 仍高，数据和 last 与前一采样值相同。若复位可在两拍间异步拉低，禁用会中止匹配，通常符合复位取消事务的契约。若协议允许 flush 撤销 valid，应把 flush 写成明确取消分支。历史不足和首次采样需处理。

assert property (@(posedge clk) disable iff (!rst_n)
  req |-> ##[1:MAX_LAT] ack);

该属性要求每次采到 req 后 1 到 MAX_LAT 个采样事件内出现 ack。若 req 连续有效，ack 是否满足每个请求取决于 req 是电平还是事务事件；应使用握手、边沿触发或 outstanding 计数定义事务。无界弱序列 ##[1:$] ack 可以始终 pending；蕴含因此不一定要求在有限执行结束前出现 ack。若规格要求最终匹配，应表达为 strong(##[1:$] ack) 或使用工具支持的 s_eventually 等活性构造，并确认工具执行了适当的 liveness 分析。公平环境假设和活性设置必须与系统条件一致。

27.3 空洞性、重叠与历史

蕴含式 antecedent 从不成立时通常仍通过，即 vacuous success。若环境永不发 req，则 req |-> ack 通过却没有检查响应。需增加 cover 观察 antecedent 可达，并覆盖“请求接受、背压至少一拍、最终完成”。形式报告中的 vacuous、unreachable、covered 分类应审阅，不能只看 pass 数。若每拍 req 会启动多个并发匹配线程；若资源只允许一个 outstanding，应检查拒绝第二笔或正确计数响应。

$past(x) 引用前次采样。起始没有足够历史时，$past 返回该变量的默认采样值：四态类型为 X，二态类型为 0。用 past_valid 屏蔽初期，避免默认值误触发属性：

logic past_valid;
always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) past_valid <= 1'b0;
  else        past_valid <= 1'b1;

assert property (@(posedge clk) disable iff (!rst_n)
  past_valid && $past(push) && !$past(pop) |-> count == $past(count) + 1'b1);

还须确认 push/pop 是已接受事件，count 的新旧采样关系正确，宽度、回绕及复位边界明确。

27.4 序列匹配和禁用边界

蕴含的 antecedent 可以是跨多周期序列。序列匹配结束时刻决定 consequent 起点；改写为较短布尔条件会改变检查位置。重叠蕴含在 antecedent 序列结束时立即检查 consequent，非重叠蕴含从下一采样事件启动。评审时将操作数标在周期表中，尤其是 $past、延迟和重复运算符混用时。范围重复会产生多条匹配线程；若要把响应绑定到请求，可用序列局部变量携带事务标识。

disable iff 在禁用条件变真时中止活动匹配，不只是停止新 antecedent。若复位断言时有 pending 请求，线程会取消；若规格要求复位时也报告事务丢失，就要另写取消或错误规则。同步复位可作为属性条件显式约束采样；异步复位与时钟沿同一仿真时刻的竞争，应按标准语义和仿真器调度处理。cover 记录发生，不自动检查结果正确；cover req 不代表响应完成，完整轨迹应 cover 请求后 ack。assertion action block 可打印上下文，但不得改变被检查状态。

27.5 安全、活性与公平性

安全性质表示坏事不会发生，可由有限反例证伪，如不溢出、不重复响应、数据稳定。活性表示好事最终发生，例如每笔请求最终有响应。活性依赖环境假设：若下游可永久拉低 ready，DUT 无法保证事务完成。公平性假设须反映实际系统，例如“连续 K 拍内至少一次 ready”，并标明复位阶段和合法场景；假设过强会把真实死锁排除。把 DUT 输出误写为 assumption 会直接假设正确性。

形式环境将输入合法性写为 assume，将 DUT 行为写为 assert；模块角色变化时，主从 checker 的 assume/assert 也要相应变化。至少用 cover 检查假设集合允许有意义事务。复位初值、未初始化存储器、参数约束和时钟关系都应显式建模。

检查：每条属性可翻成自然语言；触发是电平还是事务；旧采样与 NBA 新值区分；reset 是同步条件还是异步中止；历史有效期已处理；活性有公平前提；assume 不约束 DUT 输出；关键触发、响应和边界有 cover；工具语法支持确认；失败可从采样序列解释。

练习：req |-> ##[1:$] ack 通过，能否证明请求最终完成？答案：不能。无界弱序列可保持 pending 而不失败，req 不可达还会产生空洞通过。用 strong(##[1:$] ack) 或工具支持的最终性构造表达要求，再 cover 请求，并审查公平假设和 liveness 证明结果；若合同规定最大响应时间，优先给出有界时延属性。

第28章　面向 RTL 设计者的轻量 Testbench

28.1 TB 也要定义时序

轻量 TB 适合模块级定向和随机回归，不要求先上完整 UVM；仍需驱动器、监视器、参考模型、checker、时钟复位和结束条件。若 TB 在 @(posedge clk) 的 Active 区改输入，而 DUT 的 always_ff 也在此区采样，进程先后不确定。可在下降沿驱动、上升沿采样，或用 clocking block 指定 skew。不要用任意 #1 遮盖竞态；时间单位改变会改变延迟意义。

clocking cb @(posedge clk);
  default input #1step output negedge;
  output valid, data;
  input ready, out_valid, out_data;
endclocking

要核对 clocking block skew 与仿真器支持。简单替代是下降沿驱动、上升沿采样，前提半周期足够且接口共同遵守：

半周期 TB 行为 DUT 含义
下降沿后 设置 valid/data 输入有半周期稳定时间
上升沿前 保持输入 建立窗口
上升沿 不改输入 DUT 采样握手
上升沿后 NBA 监视输出 读取新寄存器状态

并发断言仍按自己的采样语义读取沿上的值，不能把 NBA 后观察值与 SVA 采样值混为一谈。

28.2 参考模型按握手推进

task automatic send(input logic [31:0] payload);
  @(negedge clk);
  valid = 1'b1;
  data  = payload;
  do @(posedge clk); while (!ready);
  @(negedge clk);
  valid = 1'b0;
endtask

任务默认 reset 不打断、单一发送线程、无多个 outstanding；通用 TB 要处理 reset abort、并行 sequence 和驱动器仲裁。scoreboard 在 valid && ready 同一采样沿入队；输出也按握手出队。比较数据、顺序、ID 和 sideband，记录错误时刻、队列内容、seed 和接口状态。允许同拍输入输出时，先定义事件顺序，避免模型因进程调度而改变结果。

随机化只生成协议合法输入。先用 directed test 覆盖空、满、边界、单/多事务、背压和复位，再增加随机停顿、数据和复位。每次失败需记录 seed、命令和配置；波形围绕首个差异生成，避免只有庞大数据库没有诊断摘要。

28.3 TB 并发线程与重置

多个 TB 进程同时驱动同一接口会产生竞态。将 stimulus、reset driver 和 protocol driver 分开时，应通过统一仲裁保证唯一驱动者；否则失败可能不可重现。task 无限等待须有超时，并打印事务 ID、等待条件和 DUT 状态。取消驱动时要清理 valid，不能遗留上一笔数据。

重置模型的时机应与 DUT 契约一致。异步 reset 立即取消事务时，reference queue 在断言事件清空；同步 reset 则在对应采样点清除。异步 FIFO 两域模型可能需共同 reset 后等待双方 ready；不能单边复位就无条件清全局队列，除非系统合同规定 flush。复位既是刺激也是协议事件，模型应反映其语义。

断言适合检查每拍不变量，cover 统计场景，scoreboard 检查长事务顺序。小型 TB 可由 task、queue 和 property 构成；代码量少不等于检查弱，关键是职责与观察契约清楚。随机测试需控制 seed 和随机约束，避免非法输入占据大多数运行时间；合法边界要有定向测试，随机测试负责交错。失败缩减可固定 seed 后逐步删减事务，找到最短复现序列。

28.4 CDC 仿真边界与结束条件

普通 RTL 仿真不会真实模拟亚稳解析。CDC 验证可用结构检查、专用 metastability 注入、随机相位扰动和协议属性发现逻辑缺陷，但随机化不是 MTBF 证明。异步 FIFO 应使用互不整除时钟、相位漂移、时钟暂停等情景验证顺序、边界和复位；有限随机比率不覆盖所有相位，物理约束仍需独立检查。

测试不能因 $finish 就叫通过。应等待 outstanding 事务完成，检查 scoreboard 为空、断言无失败、错误计数归零和预期覆盖达到；另加 watchdog 防死锁。watchdog 应打印当前状态和未完成请求。日志区分 PASS、FAIL、TIMEOUT、SKIP，并把失败状态返回自动化系统。

检查：驱动/采样避开竞态；只在握手时完成事务；模型按同一采样沿更新；复位清理策略明确；同拍输入输出顺序确定；随机输入合法；结束前队列为空；超时报状态；seed 可重现；仿真未冒充 CDC 物理证明。

练习：何时将 FIFO 写数据压入 scoreboard？答案：采样到 wr_valid && wr_ready 的边沿；读端在 rd_valid && rd_ready 时比对并弹出队首。若允许同拍读到刚写入的新项，按接口定义确定同时入队/出队顺序；不能因 valid 单独为真就更新。

第29章　静态检查、形式化与质量门禁

29.1 检查手段各有边界

Lint 不执行完整输入序列，也能揭示隐式位宽/符号转换、未驱动/未使用信号、锁存器、组合环、未完整赋值和可疑复位。综合检查确认预期寄存器、存储器和时钟结构被推断。CDC/RDC 工具按拓扑找跨域和复位域风险。STA 验证实现路径满足约束。形式化在声明模型、参数与假设下检查所有可能行为。工具不知道产品需求；报告必须映射到契约。

若每个 lint 告警都豁免，门禁将失去价值。豁免应有唯一 ID、对象范围、原因、影响、复核人与失效条件；RTL 改动后重查。不要用全局 waiver 隐藏整个类别。规则、severity、工具版本、命令和配置应入库，保证本地和 CI 一致。

29.2 形式化假设审计

形式化把输入和状态纳入状态空间，在约束下证明断言或给反例。它无需手写序列即可系统搜索边界组合，但范围受模型、assumption、黑盒和抽象影响。若假设 ready 恒为 1，背压路径被排除；若假设 req 永不连续，可能排除合法并发。假设只描述外部合同，每项需有需求来源，并用 cover 检查事务、背压、复位和边界可达。

安全性质通常以有限反例否定；活性要说明最终性和公平性，工具配置需能处理。不可达状态可能是设计保护充分，也可能是约束过强或初始化错误。断言通过但 cover 永不可达时不能报成功。反例要判断是 DUT 缺陷、非法环境、模型错误还是初始化/X 抽象问题；不能为消掉反例随手加假设。

29.3 等价性与分层门禁

等价性检查可证明优化前后在规定输入、状态映射和复位假设下行为一致。若有意改变延迟、吞吐或复位行为，须定义允许的序列/延迟关系，不能强求逐周期相等。形式属性、等价、仿真和实现签核覆盖不同风险。

阶段 必需证据 失败处理
本地提交 语法、格式、增量 lint 修复后重交；有据豁免
合并前 全量 lint、仿真、断言、CDC/RDC 归属缺陷、修复并重跑
发布前 形式/等价、STA、结构与豁免审查 不符合需求不签核

门禁不应仅依赖“全绿”状态码。日志、未运行项目、工具崩溃、跳过测试、无覆盖任务都要显式标注。产物关联版本、约束、参数、工具版本和签核人。未执行不能汇报为通过。

29.4 CI 门禁的可操作性

门禁按风险与耗时分层：提交时执行语法、快速 lint 和局部单元测试；合并前跑全量仿真、CDC/RDC 和关键形式属性；发布前用冻结配置跑 STA、等价性和完整签核。跳过项目显示 skipped 并说明阻断条件或替代证据；工具崩溃归类为基础设施失败，不可伪装成通过。

基线管理需分开新增与历史告警。已有批准的 legacy 告警不应让新增同类告警自动通过；修复后删除旧 waiver，避免其扩展覆盖无关对象。看板可展示未约束路径、未审豁免、不可达 cover、未运行配置和回归积压，而不只给通过率。CDC 安全性、formal assumptions 是否符合系统、false path 是否有效、PPA 是否同条件比较，仍需人工审阅并记录责任人、依据和边界。接口、时钟关系或工具版本变化时重新复核，防止过期豁免长期沿用。

29.5 反例演练与审查

计数器 8 位，断言要求 count<200；formal 未建模 reset，从任意初态开始，给出 count=255 的反例。正确做法不是直接 assume count<200，而是明确初始化合同：复位把状态置零，证明 reset 可发生且释放后不破坏不变量；若上电值确实任意，设计须自恢复，或属性限定有效阶段。另一例是 req |-> ack 证明通过，但环境将 req 约束为 0；cover 会揭示空洞。

检查：工具与版本可复现；lint 阻断规则清楚；豁免范围具体；假设来自外部契约；关键属性有可达 cover；活性未误报为普通安全证明；初始化、复位、非法参数建模；失败/跳过可区分；门禁按风险分层；结果关联提交和约束快照。

练习：formal 证明 FIFO 的 assert(!overflow)，而 cover(write && full) 不可达，是否说明满写不会发生？答案：只说明在当前假设与模型下满写不可达，不能证明合法环境中永不会满。检查 cover 不可达原因、输入约束和 full 建模；若合同允许满时请求，需验证背压/拒绝行为；若合同禁止，须由上游合同和集成验证共同支撑。

第30章 编码规范与 Review：让意图可以被检查

30.1 规范的作用不是统一审美

编码规范的价值不在于让所有 RTL 看起来一模一样，而在于降低读者推断硬件行为的成本，并把容易出错的选择固定下来。RTL 同时描述状态转移、组合逻辑、时序边界和工具映射意图。若同一工程里有人用阻塞赋值写时序状态、有人用非阻塞赋值，有人把复位优先级藏在嵌套条件里，Review 就必须先猜作者意图，再判断逻辑正确性。可执行规范应回答“看到这段代码时如何判断它意味着什么”，而不是只列排版偏好。

规范应分层。第一层是语言与项目约束，例如使用 SystemVerilog 哪个子集、是否允许 interface、哪些构造禁止综合；第二层是语义约定，例如时序块采用 always_ff、组合块采用 always_comb、状态寄存器统一非阻塞赋值；第三层是表达约定，例如端口方向、位宽、复位极性、命名和注释；第四层是工具检查和例外治理，例如 lint、CDC、综合和时序报告由谁执行、失败门槛是什么。工具支持随版本变化，规范不能把某个工具的偶然默认行为误写成语言规则。AMD 的综合指南提供面向 Vivado 的 RTL 编码与综合建议，适合作为特定工具链参考，不能替代 IEEE 语义或其他工具的规则。[S1]

规范还应明确责任边界。设计者负责接口契约、复位与时钟关系、跨域策略、状态机合法状态和参数边界；Review 者负责挑战隐含假设、检查边界与错误处理；工具负责发现语法、位宽、未驱动信号、锁存器推断等可自动识别的问题；项目负责人维护例外记录并定期清理。若任何一层都声称“工具会兜底”，却没有具体命令、版本、输入文件集和失败门槛，这条规范便不可执行。

30.2 Review 的阅读顺序

Review 不宜从变量名逐字挑起。先读模块接口和规格：握手是否允许同拍接受与完成，ready 是否可组合回传，输入何时被采样，复位后哪些输出必须有效。接着检查时钟、复位、跨域和状态：一个状态变量是否只有一个时序驱动，异步输入是否经过明确 CDC 结构，复位释放策略是否符合系统要求。然后检查数据路径和边界：位宽、符号扩展、截断、移位量、计数器终值、数组范围、参数最小值/最大值。最后再看结构与风格：是否存在重复逻辑、超长组合链、难以复用的常量、含糊注释。

Review 的核心问题是“代码在最不方便的输入与时序下仍然表达规格吗”。对每个条件分支，问条件是否互斥且完备、未命中分支的值从哪里来、状态更新在本拍还是下一拍生效、两个事件同拍时哪个优先、复位与使能同时有效时谁优先。对于握手协议，若 valid 连续保持而 ready 拉低，数据和控制是否稳定？若 FIFO 满与读写同拍，计数和指针规则是否定义？只有把时序语义说清楚，Review 才不会沦为“看起来没问题”。

常见反例是用不完整组合赋值掩盖状态保持：

always_comb begin
  if (sel)
    y = a;
end

当 sel 为 0 时，y 保留旧值，需要锁存器实现，通常并非设计者预期。应给出完整赋值：

always_comb begin
  y = '0;
  if (sel)
    y = a;
end

但“先默认零”不是万能修复：若 y 的语义确实是状态保持，它应是时序寄存器，不能通过组合默认值改变行为。Review 既要识别结构错误，也要防止为了消警告而改变规格。

另一个反例是多个过程块写同一寄存器：

always_ff @(posedge clk)
  if (set) q <= 1'b1;

always_ff @(posedge clk)
  if (clear) q <= 1'b0;

即使仿真在某种调度下看似稳定，双重驱动仍让优先级和可综合性不清晰。应合并为一个状态更新过程，明确 clear 和 set 的优先次序。类似地，时序过程里使用阻塞赋值会令同一过程内语句顺序影响仿真可见值；团队应约定时序状态使用非阻塞赋值，组合临时量使用阻塞赋值，并在工具允许时用 always_ff / always_comb 显式表达过程种类。

30.3 用规则处理例外

规则必须可判定。例如“命名要清晰”很难审查；“时钟端口后缀 _clk、低有效复位后缀 _rst_n，复位极性必须在接口文档说明”更可检查。规则也要写理由：宽度表达式可以减少魔数；枚举状态类型提升可读性，但状态编码是否由综合器选择、是否需要固定编码，应由安全与实现要求决定；unique case 能表达互斥/完整性意图，但非法编码处理仍需明确，不能把仿真检查当作硬件恢复电路。

编码规范不应鼓励整体关闭 lint 警告。Verilator 文档说明可以按规则、文件和行区间配置警告，也提供 lint-only 流程；这是精确处理遗留或已审查例外的能力，不是全工程无条件禁用警告的理由。[S2][S3] 每个 waiver 至少记录警告编号、文件与行、原因、潜在风险、替代检查、责任人或模块负责人、复查条件。使用文件级或全局抑制之前，应先确认是否能通过修正代码、局部注释或精确规则选项处理。全局关闭可能把未来新增的真实缺陷也遮住。

Review 也需要明确“阻断”与“建议”。功能不确定、接口契约缺失、CDC 结构错误、综合出锁存器、关键路径无约束等应阻断合入；命名小偏差、可读性提升等可作为非阻断意见。意见应指出代码位置、输入条件和风险，不应只写“这里不对”。较好的评论是：“当 count == LIMIT-1 且 enable 连续为 1 时，下一拍会回绕；规格是否要求饱和？请明确后给出断言。”作者便可围绕行为而非个人风格作答。

30.4 Review 练习与答案

练习： 某计数器在 enable 为 1 时递增，达到 MAX 后回到 0。Review 时应提出哪些问题？

参考答案： 首先确认 MAX 是最后一个计数值还是计数模数：若计数值范围是 0 到 MAX，回卷条件是 count == MAX；若范围是 0 到 MAX-1，条件应是 MAX-1。其次检查 MAX 参数的位宽和最小合法值，MAX=0 是否允许，表达式 MAX-1 是否在无符号运算下下溢。再次确认复位值、复位极性和复位同步/异步要求。最后明确 enable 在终值拍拉低时是否保持终值，以及终值命中后该拍输出代表旧值还是新值，并用断言或定向测试锁定这些行为。不能只凭“计数到最大值”决定实现。

本章小结： 好规范应改善行为理解、自动检查和例外追踪。Review 从契约与时序进入，再检查位宽边界、状态完整性和映射风险。规范不是代替工程判断，而是让判断理由可以复用。

第31章 可维护参数与可复用 IP：把变化限制在边界内

31.1 复用的对象是契约，不是源代码片段

可复用 IP 的基本单位不是“有参数的模块”，而是一份可验证契约：输入输出含义、时钟与复位条件、吞吐率和延迟、背压行为、参数合法范围、异常输入处理以及实现限制。将常数改成参数并不自动带来复用；若参数组合导致零宽向量、数组越界、不可实现的分频值或协议永不完成，这只是把一个固定缺陷扩展为一族缺陷。

参数化设计应从变化点开始，而不是追求参数数量。找出工程中真实会变化的量：数据宽度、队列深度、通道数、地址宽度、是否带奇偶校验、目标时钟对应的分频系数。固定规则则保留为实现约束。一个 FIFO 可能只有宽度和深度值得参数化；把指针编码、复位值、输出空闲值和内部比较算法都暴露成参数，会增加验证空间，也让集成者误以为这些点均受支持。

每个参数要有类型、默认值、合法范围和相互约束。使用 parameter int unsigned DATA_W = 32 比无类型常数清楚；使用 localparam 派生 PTR_W、COUNT_W 可使依赖关系集中计算。对 $clog2，深度为 1 时结果为 0，因此常见的 PTR_W=$clog2(DEPTH) 会产生零宽问题。若指针至少一位，可用 PTR_W=(DEPTH<=1)?1:$clog2(DEPTH)，但还必须说明深度 1 是否支持、指针是否另有回绕位。避免“看上去总能综合”的算式遮蔽数学边界。

反例：一个模块把 WIDTH 作为无类型参数，再声明 [WIDTH-1:0]。WIDTH=0 时端口范围失效；表达式的有符号性和位宽还可能随上下文变化。更可靠的接口会限制参数，并在 elaboration 阶段或静态检查中报告非法配置。SystemVerilog 没有所有工具通用的参数断言机制，工程可用 generate if 配合仿真检查，也可由构建脚本检查参数。关键是说明检查在哪个流程运行，不能假设综合器一定以相同方式处理仿真专用错误语句。

31.2 参数矩阵与组合爆炸

若一个 IP 有 5 个可选参数，每个参数有 2 种取值，完整组合已有 32 种；参数再增多，验证成本迅速扩大。应把配置分为三类：保证支持并纳入常规回归的配置；语法上允许、但需集成方验证的配置；明确非法并应尽早报错的配置。不要用“参数理论上可以改”暗示所有组合均已验证。可以为常见配置建立清单，例如小深度/大宽度、非二次幂深度、最小计数宽度、功能可选项关闭。边界配置往往比默认配置更易暴露截断与终止条件错误。

参数依赖应沿一个方向派生，避免互相覆盖。顶层尽量只传递用户可配置参数，内部尺寸用 localparam 从源参数推导。若把 DEPTH 与 PTR_W 同时开放，集成者可能传入相互矛盾值，造成数组与指针语义不一致。确需固定物理映射或外部总线宽度时，暴露二者有理由，但必须加一致性检查，并列出合法配置。

参数也会影响接口语义。例如 DATA_W=1 时字节使能是否存在？DEPTH 非 2 的幂时指针能否正确回绕？数据宽度不满一字节时奇偶校验位是否独立？ADDR_W 小于地址窗口要求时地址比较是否截断？Review 与验证计划应覆盖这些语义，而不仅是编译通过。若限制深度必须为 2 的幂，应明确拒绝其他值，不要依赖比较器恰好“能工作”。

31.3 接口稳定性与兼容策略

可复用 IP 的接口文档应解释每个端口的采样点和驱动时机。对 ready/valid 接口，写清楚传输发生于时钟沿且 valid && ready 为真，说明 valid 等待期间负载是否保持不变，复位时 valid 如何处理。对脉冲接口，说明脉冲宽度、最小间隔和跨时钟域策略。对寄存器接口，说明读写副作用、未实现地址行为、保留位读值与写入策略。

接口升级应尽量保持兼容。添加可选功能时，默认配置应维持旧行为；改变复位极性、流水延迟、握手接受条件或错误输出定义属于契约变更，需要版本或迁移说明。不要把内部状态编码、实现级 RAM 推断细节当作稳定接口承诺，除非系统确有依赖。另一方面，某些实现假设必须公开，例如时钟频率上限、复位释放要求、存储器读延迟、CDC 约束、仿真模型与综合宏的差异。

IP 包应包含 RTL、参数说明、接口说明、约束模板、lint/综合使用说明、最小集成示例和验证入口。不要把用户环境相关绝对路径写入脚本，也不要把生成文件与手写源混在一起。构建应通过受控文件清单确定源文件次序和宏定义；隐式通配符可能把临时文件或旧版本一并编入，导致“本地能过、干净环境失败”。参数默认值、工具版本、编译选项和约束版本都应随 IP 交付。

31.4 权衡与练习答案

更高抽象度能降低重复，却可能让实现意图更难被工具识别。通用队列支持任意深度，验证和地址回绕更复杂；限定为 2 的幂便于指针自然溢出和存储器映射，却牺牲配置自由。可选功能用参数关闭，可能改变资源结构，也增加配置覆盖；拆成不同模块则边界清晰，却会引入组合维护成本。决策应以用户需求、目标工具与可验证范围为依据，并在文档说明限制。

练习： 为参数化 FIFO 设计，最少要检查哪些边界？

参考答案： 至少检查 DATA_W 的最小、常用和较大值；DEPTH=1、最小允许深度、非 2 的幂深度（若允许）和最大允许深度；验证读写指针位宽、计数器范围、满空条件、同拍读写、满时写、空时读、复位后的指针/计数一致性。还要检查输出是组合读还是寄存读、读延迟是否因参数变化而变更。若只允许 2 的幂深度，构建或 elaboration 检查必须拒绝非法值。不能只说“把参数扫一遍”，而不定义支持范围和关键行为。

本章小结： 参数化不是把常量替换为变量，而是界定支持配置族并管理验证组合。先稳定契约，后开放必要变化点；派生宽度集中计算；边界条件在设计、构建和验证三处形成闭环。

第32章 PPA 优化闭环：每次改变都能解释

32.1 先定义目标，再看 RTL

PPA 分别指功耗、性能和面积，但三者并非可以独立最大化。更高频率可能需要更深流水线，面积因此增加并带来时钟功耗；门控可能降低动态功耗，却增加时钟树、测试和时序复杂度；资源共享可以减少算术单元，但增加多路选择器和关键路径。优化前应写出优先级、硬约束和允许的功能变化。例如时钟周期、最大面积、功耗目标、吞吐率、延迟上限，以及是否允许增加寄存器。没有目标的“优化 RTL”往往只是把代码改得更短。

PPA 闭环第一步是建立可重复基线：同一 RTL 版本、约束文件、工具版本、器件/工艺库、综合选项和实现策略。记录输入版本哈希、顶层、宏、参数、时钟约束、I/O 延迟、例外约束、运行阶段和报告。只比较相同阶段与相同条件的结果。综合估算、布局后、布线后数字具有不同可信度，不可混为一谈。AMD 方法论强调工具流程中的估算精度会随实现阶段推进而提高，并建议从早期就提供正确时序约束；其报告指南区分 timing summary、利用率和 CDC 等分析用途。[S4][S5][S6]

第二步是检查输入质量。缺失时钟、过度宽泛的 false path、无效时钟周期、错误 I/O 延迟、未约束路径会让优化器针对错误目标工作。对 FPGA，错误约束可能造成工具没有优化真正关键路径；对 ASIC，库、角、RC 与约束场景不完整同样会使比较失真。跨域路径不能仅靠把 timing exception 加大或全局切断来“消除”报告。AMD 文档区分 CDC 结构报告与时序松弛信息，report_cdc 关注跨域结构及相关约束而不提供 slack；因此它与时序报告互补，不能相互替代。[S7]

第三步是定位瓶颈，而不是猜。阅读最差路径起点/终点、逻辑级数、扇出、布线占比、寄存器/存储器映射、拥塞和利用率。面积目标则看资源类型、层级和重复结构；功耗分析要辨别时钟、开关活动、漏电与约束假设。不同工具有各自报告名和建模能力，应遵循目标工具官方指南。本书不把任一单一报告当成完整 PPA 证明。

32.2 一次只检验一个假设

改动前先写下假设，例如“将串行比较改为分层比较，可缩短关键路径，但会增加少量组合单元”，再列出功能风险、验证方法和回退条件。一次提交尽量只改变一个结构因素，否则即便结果改善也难以知道收益来自哪里；若结果变差也难以定位原因。每次变化后先做等价性或功能验证，再跑相同设置的综合与实现流程。对行为改变，必须更新规格、断言和测试；不能用“综合面积更小”抵消功能不一致。

常见优化方向各有代价：

  • 逻辑重构： 消除冗余比较、共享条件、简化布尔表达。工具通常会做局部优化，手工重写不保证更好；清晰语义优先，结果以实现报告为准。
  • 流水线： 将长组合路径分段，可提高可达频率，但增加延迟、寄存器面积和时钟负载，并可能改变协议对齐。必须定义有效位随数据同行的延迟关系。
  • 资源共享： 多个运算复用单元可减少面积，但选择器、控制和扇出可能延长关键路径，吞吐率也可能下降。
  • 并行化/复制： 可提升吞吐率或减少扇出，却增加面积和动态功耗，还可能加剧布线拥塞。
  • 存储器推断： 采用同步读写等目标 RAM 友好模板，可能节省触发器；端口数、读延迟、复位内容与字节使能均可能受限。
  • 扇出与层级： 复制控制逻辑或局部化信号可能改善布线；手工复制也可能增加面积并妨碍综合器共享。

反例是仅凭 RTL 行数或运算符数量判定质量：将 a+b+c+d 改写成树形结构不必然降低实际延迟，综合器可能已完成重平衡，或者目标器件进位链对原写法更合适。把多个条件合成一个长布尔式，可能让读者误判优先级，也不一定减少硬件。结构改变必须由目标工具结果证明。

32.3 约束与报告共同构成证据

关键路径优化依赖正确的时钟定义、输入/输出延迟、时钟不确定度、生成时钟和例外。例外约束应对应明确的功能理由和 CDC/协议证据，保留来源、范围和审查记录。过宽 set_false_path 会移除真实时序检查；多位异步总线不能因单比特同步器经验而被当作安全。AMD 约束指南列出 CDC 可按场景使用 false path、clock groups、datapath-only max delay 和 bus skew 等约束；选项针对不同分析目的，需结合结构检查，不能互相替代地套用。[S8]

报告中至少保留综合警告与锁存器检查、资源利用率、时钟与路径摘要、关键路径明细、CDC 检查结果，以及与目标相关的功耗估算。比较结果时记下“改善什么、牺牲什么、证据在哪里”。如果面积降低但时序超标，这不是整体改善；如果时序改善依赖错误切断路径，也不是有效闭环。报告结论应写出工具版本和运行阶段，并标明估算/签核属性。不可把不同器件、不同约束或不同实现阶段数字直接横向比较。

功耗尤其容易被误读。动态功耗估算依赖活动率和电容，若没有真实活动文件，默认向量或静态概率可能与实际 workload 不符；漏电随工艺、温度、电压变化。因此功耗优化应说明活动输入和分析角，必要时区分早期估算与后期分析。不得把一个工具报告的估值写成实测功耗，也不应在数据缺失时编造百分比。

32.4 练习与答案

练习： 一次修改后综合面积下降，但最差时序恶化，能否称为优化？

参考答案： 不能脱离目标函数判断。若最高时钟是硬约束，恶化后超限则此修改不可接受；若时序仍有裕量而面积是当前瓶颈，可能是合理的面积/时序交换，但必须证明完整实现阶段仍满足约束，并记录裕量及其它代价。还要确认约束和运行设置完全一致，检查关键路径是否迁移、是否引入新高扇出、吞吐率与延迟是否变化。若报告来自综合阶段，只能得出综合阶段结论，不应宣称最终 PPA 已改善。

本章小结： 有效的 PPA 闭环包含目标、基线、约束、瓶颈、单一假设、等价/功能证据、实现报告和回退条件。工具数值只有在输入和阶段清楚时才可比较。

第33章 工程交付：让结果可复现、可接手

33.1 交付不等于提交 RTL 文件

工程交付要回答接手者的四个问题：哪些文件组成设计，怎样构建，怎样判断构建成功，哪些限制和风险尚未解决。只交几个 .sv 文件而不交文件清单、宏定义、约束、工具版本和参数配置，接手者可能得到另一个设计。文件清单要显式列出源码、包、接口定义、宏、约束、仿真模型和必要 IP；优先用受控清单或工程脚本，不依赖本机 IDE 的隐式状态。相对路径应相对于仓库或脚本位置解析，避免个人绝对路径。

交付包要包含可复现配置：顶层模块、参数值、编译/综合定义、工具和版本、目标器件或库、时钟与 I/O 约束、构建入口、报告输出目录和退出码规则。若工具许可证、IP 核或第三方模型无法随包分发，须说明获取方式及版本，不要把缺失依赖伪装成已验证。构建日志与报告应能关联到源代码提交和配置哈希。对于生成文件，明确它们是源码还是构建产物、哪些可重生成，避免过期生成代码被当作权威实现。

最小交付说明可以包含：

模块/版本：
接口与参数文档：
源文件清单：rtl/files.f
约束入口：约定的 SDC/XDC
构建入口：scripts/build.*
验证入口：lint / sim / 工程流程说明
已知限制：参数范围、时钟/复位要求、未支持功能
结果状态：未运行 / 已运行（工具、版本、命令、日期、结果摘要）

“结果状态”必须诚实具体。若只做静态审查，就写静态审查；若没有运行综合，就不应写“综合通过”。即便运行一次仿真，也不能推断 CDC、时序和物理实现均通过。工程交付记录要区分已验证事实、工具估算和待验证假设。

33.2 版本管理与变更记录

一次有意义的提交应围绕一个变更目的，描述行为变化和风险。不要把功能、格式化、文件迁移和约束重写混成一个难以审查的提交。接口变化要标明兼容性影响；参数默认值变更要说明会改变哪些实例；约束变化要列出路径范围和理由。生成文件若由脚本生成，应记录生成器版本和输入；手工编辑生成文件而未同步输入，下一次构建会丢失修复。

交付记录至少保留提交标识、修改摘要、涉及模块、接口/参数变化、验证命令、工具版本、结果文件位置、已知问题、未完成事项、回退方式。硬件项目跨团队和跨时间复用，单凭“fix timing”无法复现当时环境。不要把个人机器临时目录、访问令牌、许可证路径或客户数据写入日志。需传递的第三方 IP 和模型要核对许可与分发限制。

33.3 质量门槛与交付决策

交付门槛应由项目风险决定。基础门槛通常包括语法/elaboration 无错误、关键 lint 警告有处理结论、未预期锁存器/多驱动为零、接口契约更新、参数配置属于支持矩阵、CDC 与时序约束经过审查、目标阶段报告可追溯。不能把“警告数归零”当作唯一目标，因为错误抑制也能让数字归零。应为已知例外建立明确 waiver，并保证例外不掩盖新增问题。

如果某流程阶段未运行，交付仍可进行，但必须把状态标为未验证并说明接手前置条件。对于安全相关或高可靠用途，哪些报告是发布阻断条件应由系统安全流程定义，不能由 RTL 作者自行降低门槛。对一般模块，合理门槛也应在开发开始时确定，避免临近交付才因报告缺失争论。

交付审查应抽查干净环境构建。常见“我机器上能过”的原因包括依赖 IDE 遗留 include 路径、未提交 package 文件、大小写差异、宏定义在本机全局配置、文件列表顺序依赖、工具版本不同、生成文件过期。干净环境构建入口要能从仓库根目录或明确指定工作目录运行，失败时返回非零状态，并给出易定位错误信息。若无法在目标环境运行，应把限制写在交付说明中。

证据链还要区分“可复现输入”和“可复现结果”。保存 RTL、约束、参数与命令，只说明有机会重建；第三方 IP、工具补丁、库版本、随机种子、环境变量和运行策略若不同，结果仍可能变化。对于综合及实现流程，应记录影响结果的主要配置，并将日志和报告按版本归档；无需把庞大临时数据库一律提交，但需明确如何重新生成、归档多久、由谁维护。对于随机化验证，应保存种子和失败用例，且说明种子是否足以确定重放。对仿真波形，应保留失败时的必要波形或事务记录，而不是用截图替代可定位的文本日志。交付审查者要能从报告追溯到源版本，从源版本找到构建命令，并从构建命令识别缺失依赖。若其中任一环断开，结论的可复核性就下降。

交付还涉及信息与许可管理。不要在公开仓库或报告里放客户设计数据、密钥、个人账户令牌和未授权供应商模型；交付前确认第三方 IP 的分发许可、加密文件的访问控制和日志脱敏方式。此类检查不是形式上的行政步骤：一旦把禁止传播的模型打入归档，后续撤回可能无法消除已复制的副本。最小化交付内容、明确访问人群、保留必要审计记录，能在完整性和可控性之间取得实际平衡。

33.4 练习与答案

练习： 一个 IP 的 RTL 与 testbench 已提交，仿真在开发者电脑通过，但没有约束文件和工具版本记录。能否标记为“交付完成”？

参考答案： 可以称“源码与仿真结果已提交”，不能据此称“完整工程交付”或“时序已验证”。应补齐或明确不适用的约束入口、构建文件清单、参数配置、工具版本与命令、仿真日志/结果摘要和已知限制。若 IP 只作为无时钟纯组合模型使用，也要说明时序约束不适用理由。接手者需能区分已发生的验证与尚未发生的验证，并按记录重现构建。

本章小结： 可交付 RTL 是源码、接口契约、约束、配置、构建入口、结果证据和已知限制的组合。工程包质量以他人能否定位输入、重建结果并理解剩余风险来衡量。

附录A 常用 Verilog/SystemVerilog 语法速查

本附录是工程阅读速查，不取代 IEEE 1800 标准或目标工具手册。编译器和综合器支持的语言子集可能不同，项目应固定工具版本和语言模式。

A.1 类型与声明

logic                 valid;
logic [31:0]          data;
logic signed [15:0]   sample;
typedef enum logic [1:0] {IDLE, RUN, DONE} state_t;
state_t state_q, state_d;
localparam int unsigned DEPTH = 16;

logic 是四态变量类型，可用于多数 RTL 信号声明；bit 是二态类型，适合不需要 X/Z 的 testbench 数据，但用于设计意图时应理解未知值会被压缩。wire 是网络类型，适合连续赋值和 net 语义；logic 不能随意多驱动。向量 [MSB:LSB] 的方向和宽度必须一致。int 通常是有符号 32 位，宽度或比较表达式若与无符号向量混用，可能产生意外扩展；参数优先显式限定宽度/有符号性。

A.2 过程块与赋值

always_comb begin
  next_value = current_value;
  if (load) next_value = input_value;
end

always_ff @(posedge clk or negedge rst_n) begin
  if (!rst_n) state_q <= IDLE;
  else        state_q <= state_d;
end

assign ready = (count_q < DEPTH);

组合逻辑过程应给出所有输出赋值路径；状态寄存器通常使用非阻塞赋值。always_ff、always_comb 表达设计意图并使工具更易检查，但具体诊断行为依工具而异。连续赋值适合简单组合连接。initial、延时控制、事件触发和 testbench 语法的综合支持有工具/器件差异，不要仅凭仿真能运行就认定可综合。

A.3 条件、选择与位运算

if (cond) begin
  // ...
end else begin
  // ...
end

case (opcode)
  OP_ADD: result = a + b;
  OP_XOR: result = a ^ b;
  default: result = '0;
endcase

assign packed = {header, payload};

'0 / '1 是按目标上下文扩展的未定宽常量，适用于将向量清零/置位；对算术、比较和移位，明确操作数宽度与符号性。casez / casex 会将某些位当作通配符，X/Z 被掩盖时可能隐藏仿真未知值；除非编码规范明确允许，否则更适合使用精确 case 或显式掩码。unique / priority 可表达分支关系并触发工具检查，但不能代替非法输入行为定义。

A.4 数组、结构与生成

logic [DATA_W-1:0] mem [0:DEPTH-1];
for (genvar g = 0; g < LANES; g++) begin : g_lane
  lane u_lane (...);
end

数组下标范围、方向和参数派生宽度需要统一。generate 结构在 elaboration 时决定硬件结构，循环边界必须为静态可展开表达式。打包结构体可组织同一接口数据，但跨工具、跨语言、IP 边界的打包兼容性需在接口协议中定义。模块参数优先用命名覆盖，避免位置覆盖误读。

A.5 时序与并发

硬件 RTL 中不要把软件式顺序执行误当成无条件时间顺序。多个 always 块并发执行；阻塞赋值会在当前仿真调度区立即更新，非阻塞赋值安排在 NBA 区更新。写法应让仿真调度与硬件时序模型一致，并通过单一驱动、清晰边界减少竞争。断言中的 |-> 表示同一采样时钟下的重叠蕴含；|=> 表示非重叠蕴含。精确延迟依采样事件和序列长度定义，模板须结合协议调整。

附录D 警告处理方法

警告是一条待分类的信息，不是自动判错，也不是可随意屏蔽的噪声。建议按以下顺序处理：

  1. 定位源头。 保存完整警告编号、工具版本、文件/行、实例层级和参数。确认警告来自手写 RTL、生成代码、第三方 IP 还是约束。
  2. 理解语义。 查对应工具官方规则，区分语言错误、综合限制、风格建议、可疑结构和上下文相关提示。Lint 诊断不能代替仿真或形式验证；综合器能接受也不证明规格正确。
  3. 优先修代码或输入。 常见处理是补全组合赋值、修正位宽、删除未使用信号、纠正宏、补齐时钟约束，或把真实状态保持改写为寄存器。不要仅为让报告安静而改变功能。
  4. 确需豁免时缩小范围。 按警告类型、文件和行设置局部 waiver。Verilator 控制文件可按警告规则和文件/行范围启停，命令行也能选择具体警告；项目需固定使用版本和配置文件。[S2][S3]
  5. 记录并复查。 说明警告为何不构成缺陷、仍存什么风险、由哪个替代检查覆盖、谁负责、什么条件下重新打开。第三方代码升级或行号变动时重新确认，不机械复制旧 waiver。

建议分类：

  • 必须修复： 语法/elaboration 错误、意外锁存器、未驱动关键控制、位宽截断、多个驱动、CDC 未处理、关键时钟未约束等。
  • 修正或提交理由： 未使用信号、未覆盖枚举值、隐式类型转换、未声明端口、可能不完整条件、未连接接口。
  • 允许有记录地豁免： 经审查的第三方 IP 内部警告、被验证为有意的未用参数/端口、工具不能识别的合法结构。例外须有确切范围和替代证据。

禁止把全局“禁用全部警告”作为常态配置。工具文档也建议优先清理代码、使用局部 lint 控制或精确选项，而非一概禁用警告。[S3] 报告中应分开列出警告总数、豁免数和新增数；“总数不变”仍可能包含新缺陷与旧警告互相抵消。

附录E 常用 SVA 模板与假设

下列模板假定 SystemVerilog Assertions 可用，且以 default clocking 指定采样时钟。使用前需确认工具支持、复位采样策略和协议语义。模板中的 disable iff 通常表示复位期间禁用属性，但异步复位信号如何与采样时钟交互应按工具和项目策略审查。断言放在验证环境或绑定层，避免把验证专用逻辑误综合。

default clocking cb @(posedge clk); endclocking
default disable iff (!rst_n);

E.1 Valid-ready 稳定性

property p_hold_payload_when_stalled;
  valid && !ready |=> valid && $stable(payload);
endproperty
assert property (p_hold_payload_when_stalled);

假设： 协议规定一旦 valid 拉高而未被接收，源端必须保持 valid 和负载，直到握手成功。若协议允许取消或 flush，需在前件增加取消条件或相应禁用条件。payload 应包含所有随事务绑定字段。

E.2 握手发生时接受一次

cover property (valid && ready);

假设： valid && ready 是本拍接受事务的完整定义。此 cover 只说明仿真/形式探索能到达该条件，不证明 DUT 功能正确或系统一定会发生握手。若环境必须提供公平性或最终 ready，需要另写环境假设。

E.3 请求最终响应（有界）

parameter int MAX_LAT = 8;
assert property (req |-> ##[1:MAX_LAT] rsp);

假设： DUT 规格保证每个 req 在 1 至 MAX_LAT 个采样周期内出现响应；若响应可与请求同拍，将下界改为 0。若请求可被拒绝、取消、复位清除或多个请求并行，需明确对应条件和事务匹配方式。若该责任属于环境，应改写为 assume property；把 DUT 必须满足的行为错误写成假设会锁死验证空间。

E.4 FIFO 计数边界

logic past_valid;
always_ff @(posedge clk or negedge rst_n) begin
  if (!rst_n) past_valid <= 1'b0;
  else        past_valid <= 1'b1;
end

assert property (@(posedge clk) disable iff (!rst_n)
  count <= DEPTH);
assert property (@(posedge clk) disable iff (!rst_n)
  past_valid && push && !pop && !full |=>
  count == $past(count) + 1);
assert property (@(posedge clk) disable iff (!rst_n)
  past_valid && pop && !push && !empty |=>
  count == $past(count) - 1);

假设： push/pop 是已接受操作，不是原始请求；同拍 push/pop 对计数保持不变；满时是否允许同时 pop 与 push、空时是否允许旁路，需由 FIFO 契约定义。计数器宽度应容纳 DEPTH。SVA 的 $past(expr) 在当前时钟采样点引用上一采样点的 expr；尚无前一采样点时，语言规定其结果为 expr 类型的缺省采样值（四态类型通常为 X，二态类型为 0），不应将其描述成工具任意选择的值。上例用复位清零、随后置位的 past_valid 只在确有历史样本时启用依赖 $past 的性质；该标记本身也应与属性使用相同采样时钟。复位语义若不同，应相应调整历史有效条件。

E.5 状态编码合法性

assert property (!$isunknown(state_q) && state_q inside {IDLE, RUN, DONE});

假设： 状态类型具有明确枚举值，非法/未知状态策略已定义。显式使用 !$isunknown(state_q) 可让断言先拒绝含 X/Z 的状态，再检查枚举集合成员；不要依赖 inside 的通配/匹配行为来承担未知值检测。若实现会自动重编码，断言应绑定到 RTL 抽象状态，而非门级编码值。

E.6 互斥事件与响应脉冲

assert property (!(grant_a && grant_b));
assert property (done |=> !done);

假设： 两个 grant 在任何采样点都必须互斥；done 是单周期脉冲。若连续完成事件可每拍产生，第二条不成立，应改为根据请求/接受条件描述脉冲宽度。

E.7 假设与断言的分界

验证环境对 DUT 输入施加限制时用 assume；DUT 对外承诺的行为用 assert；希望检查可达性或测试激励是否触达时用 cover。错误地把断言写成假设会令工具排除真正错误输入；错误地把环境义务写成断言，则要求 DUT 控制外部信号。每条属性旁应记录责任主体、时钟、复位期间行为、并发事务语义和是否有界。

案例 C：面向控制寄存器的 AXI4-Lite 从设备

本案例从一项很具体的外围设备需求出发：处理器经由 32 位 AXI4-Lite 总线访问一个可读写控制寄存器和一个只读识别寄存器。案例实现一个可综合的 SystemVerilog 从设备，并附带自检 testbench。重点不是把 AXI 写成一个抽象的“通用桥”，而是将地址、数据、响应三组写通道和地址、数据响应两组读通道，收敛为一个边界明确的 CSR 接口。设计允许读和写各有一个未完成事务，但不支持同方向的多笔排队；写地址和写数据可以先后到达，也可以同拍到达。

源码：axi4lite_csr.sv；自检台：tb_axi4lite_csr.sv。

1. 需求和边界

AXI4-Lite 适用于配置与状态访问。Arm 规范规定 Lite 事务长度为 1，接口数据宽度固定为 32 位或 64 位，Lite 支持写选通，而且不支持 EXOKAY 响应。本案例刻意选取常见的 32 位宽度，响应只使用 OKAY 和 SLVERR。该接口不是转换器：它不把上游 AXI 突发拆开，不做时钟转换，不保存任意深度的命令队列，也没有超时机制。

项目 本案例约定 设计理由
时钟与复位 单一 aclk；aresetn 为低有效、同步采样 状态只在上升沿变化，复位行为可在一个时钟边沿后精确描述
数据宽度 WDATA/RDATA 为 32 位，WSTRB 为 4 位 每个选通位对应一个 8 位字节通道
写地址/数据 AW、W 各自一槽；允许 AW 先、W 先或同拍；每个通道最多接收一项 满足两个独立握手通道，不把“同拍到齐”当作前提
写提交与响应 两半均已接收后，控制寄存器恰好更新一次并产生一项 B 响应；B 可背压 在 B 握手前不接受下一笔写事务，避免覆盖待回传响应
读路径 AR/R 各一项在途；R 可背压；读和写相互独立 低复杂度 CSR 的常用并发边界
地址 0x0 CTRL，读写；复位值为零；写入按 WSTRB 更新对应字节 展示寄存器字节合并的基本做法
地址 0x4 ID，只读；默认 32'hA5C3_1234，可由参数改写 固定识别值不接受写操作
其他地址 未映射地址和所有非 4 字节对齐地址返回 SLVERR；失败读的 RDATA=0；失败写不修改 CTRL 给软件一个确定的错误结果，并阻止越界地址产生副作用
AxPROT 接口保留 AWPROT/ARPROT 引脚，但本案例忽略 不暗示它实施特权级或安全隔离
复位效果 同步复位清空 AW/W 暂存、B/R 响应有效位并将 CTRL 清零；复位期间所有 READY 拉低 复位是事务的公共终止点；复位前未完成的握手/响应不在释放后重放

本案例把对齐条件定义为地址低两位为零，再做精确地址译码。因而 0x1、0x2、0x3 即使高位其余部分接近已知寄存器，也会出错；0x8 同样未映射。写 0x4 是对只读寄存器的访问错误，不会更改 ID 或 CTRL。对于 CTRL，WSTRB=4'b0000 是合法的空字节写：返回 OKAY，寄存器保持不变。这是“写事务有效但没有字节副作用”，不同于地址译码错误。

同步复位在每个时钟上升沿被采样。外部复位源若为异步信号，应在集成边界按目标芯片的复位策略同步释放；本模块本身不提供异步断言或复位同步器。复位期间，即使 VALID 已经拉高也不会握手，因为 READY 被门控为低。释放后，主设备若仍有未完成的上游请求，应由系统复位策略统一处理；从设备不可能知道该请求在其复位窗口外部是否已经被其他组件接受。

2. 接口切片与微架构

AXI 每个通道通过 VALID && READY 的上升沿握手独立传输。接收方拉低 READY 时，发送方必须保持 VALID 和载荷不变，直到握手发生。写事务包含 AW、W、B 三个通道，Lite 从设备仍不能假设 AW 和 W 必须在同一个周期出现。因此模块将 AW 地址和 W 数据分开暂存：aw_pending_q + awaddr_q 与 w_pending_q + wdata_q + wstrb_q。任一暂存槽空闲时即可接收该半边；另一半到来之前，已收下的载荷保持寄存器不变。

最重要的提交条件可表述为：

write_complete = !bvalid
               && (aw_pending || aw_handshake)
               && (w_pending  || w_handshake)

表达式把“此前已缓存”与“本周期新握手”统一起来。它覆盖三种时序：AW 先到时等 W；W 先到时等 AW；两者同拍时直接在该上升沿完成提交。提交逻辑根据 pending 标志选择旧缓存，pending 为空时则选取当前总线载荷。这样同拍路径无需经过一个额外状态周期，也不要求上游等待某个特定先后顺序。RTL 采用非阻塞赋值，提交分支最后清除两个 pending 标志；如果本次提交正好来自该周期的握手，该清除赋值覆盖先前的暂存置位，保证下一拍不会再次提交旧事务。

写提交时，地址被验证为恰好 0x0 才会执行字节合并。对 lane=0..3，当 WSTRB[lane] 为 1 时，CTRL[8*lane +: 8] 取对应的 WDATA 字节；未选通字节保留。写地址无效时照样消费完整的 AW/W 对并生成 SLVERR 响应，但不触碰控制寄存器。这样能避免非法写因实现细节而产生部分副作用。写入只在两半均握手后发生，不会在响应被主设备接受时才发生；B 通道只是告知主设备先前已经完成的写结果。

B 响应用 bvalid/bresp 两个寄存器表示。提交边沿置位 BVALID，响应码在同一边沿保存。如果 BREADY=0，BVALID 和 BRESP 保持；只有 BVALID && BREADY 的边沿才消费响应。为了把状态机限制在单笔，AWREADY 和 WREADY 在 BVALID 期间均为零；对同一写事务，尚未收到的另一半仍可在第一半的响应出现之前被接收，但 BVALID 出现意味着事务两半已经齐备，两槽已经清空。响应未被取走时不会开始第二笔写操作。

读路径以 arready = !rvalid 接收一笔 AR。握手发生时，译码结果和响应码被采样到 rdata/rresp，同时置位 RVALID。背压期间这三个信号保持不变，直到 RREADY 与 RVALID 同拍握手。读数据在 AR 接受时快照，而不是在 RREADY 最终拉高时读取。因此若 AR 先被接收，后续并发写更新 CTRL，尚未完成的读仍返回接受时的旧 CTRL 值。若 AR 接受与写提交恰在同一上升沿，读组合译码读取时钟沿前的 ctrl_q，所以该次读也返回旧值；非阻塞赋值在沿后更新控制寄存器。这个同时发生时的可见顺序是本实现的明确契约。每方向各只有一个未完成事务：BVALID 不阻塞 AR，RVALID 也不阻塞 AW/W；这让 CSR 的读写可以并行而不引入跨通道仲裁器。

AWPROT/ARPROT 被保留在接口中，但模块完全忽略它们。不要把这段 RTL 用作安全边界。总线地址也被视为 32 位字节地址，寄存器基址采用上述精确数值；若系统有地址重映射，交由互连译码完成，或者在这个案例模块前后增加明确的基址比较。

3. 周期级场景

下面的表中“边沿”指信号在上升沿被采样。ready/valid 在该边沿之前同时为 1 才构成一次传输。表里的响应时刻描述的是该上升沿之后寄存器状态的变化，因此 BVALID/RVALID 会在采样提交或地址的边沿后变为 1。

周期边沿 AWVALID/AWREADY WVALID/WREADY 状态与结果
T0 1/1，地址 0x0 0/1 AW 握手，保存地址，AW 槽满；尚未写 CTRL，无 BVALID
T1 0/0 1/1，数据与 WSTRB W 握手；地址和数据齐备，更新 CTRL、清空两个暂存槽、置 BVALID
T2..T4 0/0 0/0 若 BREADY 为 0，BVALID/BRESP 稳定不变；寄存器不会重复写入
T5 0/0 0/0 BREADY=1 与 BVALID=1 握手，响应槽清空；新的写通道最早从下一周期可接收

若 W 先于 AW，表格中前两行交换即可，数据和 strobe 暂存到 W 槽。若 AWVALID 与 WVALID 在空槽同时拉高，两者同时握手，同一个边沿看到两个“新半边”，提交逻辑直接从总线选择这两个值，随后产生一笔 B 响应。任何一种合法顺序都不会多写一次。READY 在空槽时可以预先拉高。本例主设备侧应遵循协议，不应等待 READY 才产生 VALID；同时从设备的 READY 也不依赖 VALID，因此任一侧先启动都不会形成互相等待的死锁。

读场景中，ARVALID/ARREADY 握手的边沿锁存读值和响应码。接下来若 RREADY 一直为 0，RVALID、RDATA 和 RRESP 均保持。写路径可在此期间完整地收下 AW/W 并发出 B 响应。相反，BVALID 停滞时也可接受 AR 并返回一笔读响应。这种独立性意味着读通路不受写响应背压影响，但同一方向的第二笔请求必须等前一响应完成。

复位在所有正常事务条件之前优先执行。若复位与 VALID 同周期出现，复位分支清空槽位及响应位，不产生握手副作用。若写已在复位前提交 CTRL，复位会将 CTRL 置回零；若只收到 AW 或只收到 W，半边直接丢弃；如果 B 或 R 正在等待，响应也被清除。因此复位对总线可见地终止本从设备的活动事务，而不是在复位释放后续传。系统级软件不应期待复位前请求仍有响应。

4. 协议选择与常见陷阱

AXI4-Lite 的定义是固定数据总线宽度、单拍事务。此处 RTL 仅实现 32 位版本，省略了 AWLEN/ARLEN、AWSIZE/ARSIZE、burst、ID 等非 Lite 必需信号；端口保留规范允许的 PROT 信号。WSTRB 在 32 位接口为 4 位，符合 AXI4-Lite 写 strobe 的字节选通用途。RESP 的 2 位编码只产生 OKAY=00 和 SLVERR=10。不产生 EXOKAY，也不以 DECERR 表示本地译码失败，因为该从设备在本地采用 SLVERR 作为所有非法 CSR 地址的约定；系统互连是否在更外层产生 DECERR 属于集成选择。

之所以没有在 BVALID 周期继续接受下一笔 AW/W，是为了让最小实现具有清楚的容量边界。较高吞吐量的从设备可以在前一响应等待期间接收后续写事务，但那需要额外队列保存每笔地址、数据和对应响应，不能简单地把 READY 改成常高。此处策略的代价是通道出现背压且相邻写之间有一个恢复空档；收益是响应不会和后续事务的地址、数据混淆。读侧同理，RVALID 满载时 ARREADY 拉低。

通道握手独立也带来主设备约束：AWVALID 一旦置位，直到 AWREADY 同拍前，AWVALID 和 AWADDR 必须稳定；WVALID 期间 WDATA/WSTRB 必须稳定；ARVALID 期间 ARADDR 必须稳定。响应方在 BREADY 或 RREADY 迟到时必须保持 VALID 和所有响应字段。testbench 的发送 task 都先在下降沿驱动，随后保持载荷直到采样到握手，再于下一个下降沿撤销 VALID，避免 testbench 自己违反源端行为。把 AW/W 信号只打一拍、或在 READY 为 0 时改变载荷的测试平台，不是有效的协议激励。

AxPROT 的语义涉及访问属性，不会自动保护寄存器；把它接入端口后仍需实现校验策略并验证。这个案例也没有对 WSTRB=0 作错误处理，因字节使能为零时没有寄存器位改变但事务仍合法成功。若特定芯片的软件 ABI 规定全零 strobe 是非法，应把该规定显式加入地址/写响应逻辑与测试，而不是依赖未定义的“默认行为”。

5. 验证策略和自检内容

随附 testbench 使用有限个任务驱动通道，检查关键外部可见行为，不依赖层次引用 DUT 内部寄存器。它不是完整 AXI 协议验证 IP，也没有随机序列、覆盖率数据库或形式属性。自检用例包含：

  1. 地址先到、数据后到，并写入 WSTRB=0101，读取回值确认只有 lane 0 与 lane 2 更新。
  2. 数据先到、地址后到，并用 WSTRB=1010 覆盖另两个字节。
  3. AW 与 W 同拍有效，确认无需额外假设且只得到一个响应。
  4. BREADY 拉低多个周期，检查 BVALID 和 BRESP 稳定；同时完成 ID 读取，证明读写两个方向独立。
  5. RREADY 拉低多个周期，检查 RVALID/RDATA/RRESP 稳定；在 R 响应挂起期间完成一笔写，再确认读返回 AR 握手时快照的旧值。另以 AR、AW、W 同拍握手测试 AR 读 CTRL 与写提交同沿时返回旧值。
  6. 写只读 ID、未对齐地址和未映射地址，逐笔检查 SLVERR；非法读检查 SLVERR 与零数据；最终再读 CTRL，确认非法写没有副作用。零 strobe 写单独检查为 OKAY 且 CTRL 不变。
  7. 全局 watchdog 防止握手错误让仿真无限等待；同步复位分别打断仅 AW 已收、仅 W 已收、B 背压和 R 背压场景，并检查半边不会跨复位配对、挂起响应会消失、CTRL 回到复位值。

6. 实现限制与扩展方向

这是一个受限 CSR 从设备实现，不是 AXI 互连桥，也不是适合所有系统的生产级控制器。它没有 CDC、异步 FIFO、跨时钟安全处理、请求超时、总线复位域隔离、ECC、可配置寄存器表、读写保护、错误日志、寄存器副作用类型（W1C、读清零、脉冲位）、多 ID、突发、乱序或同方向多事务队列。若 CTRL 位驱动不可逆外设动作，应进一步定义写提交相对于外围设备的时序，并确认复位中断这种动作是否安全。本例 CTRL 只是一个普通保持寄存器，没有外部 side effect，便于准确说明“收到写数据”和“提交”之间的边界。

没有超时的理由是副作用语义：若从设备因超时取消了已接受的一半请求，但上游稍后仍送来另一半，接口双方对这笔事务的归属会不一致；若控制器自动返回错误又不清楚是否已提交，则软件可能重试并造成副作用重复。要增加 timeout，必须在系统协议层定义取消、返回响应、迟到通道数据以及重试的统一语义，并确保外围副作用可幂等或有事务标识。这里选择可靠的握手与外部复位终止机制，不偷偷假装有安全的超时取消。

本例只有单时钟域。若 AW、W、AR 来源与 CSR 时钟不同，不能只对 VALID 做两级同步；数据载荷、通道配对和响应也都需要 CDC 方案。建议在两个同步域之间放置成熟的异步 AXI-Lite 桥/FIFO，并针对复位跨域顺序做专项验证。复位在本模块内部是同步有效，系统集成时必须让复位保持跨过有效时钟边沿，并使上游主设备的复位/请求状态与从设备保持一致；还要检查释放时序及外围复位相容性。

如果要提升性能，可以增加 AW/W 接收队列与 B 响应队列，但容量和 backpressure 必须共同设计；可将读通路做成多级流水，但需保存每次 AR 的译码结果并按顺序返回；可以扩展寄存器 map，但新增地址的权限、未对齐处理、WSTRB 策略、读副作用和错误码均要进入表驱动或组合译码并加入测试。每一次扩展都应保持源端在 VALID 未握手时稳定载荷、从端在 VALID 未被 READY 接受时稳定响应这些协议不变量。

容量的含义值得在系统规划时说清楚。这里的“一笔在途”不是指 AW、W、B 三个通道合计只能同时有一个高 VALID；AW 与 W 各有单独接收槽，先到的一半会被暂存，另一半仍然可以随后到达。它表示从设备至多拥有一个待配对的写命令，以及一个尚未被主设备消费的 B 响应。响应握手以后，下一笔写才可开始。读侧的一笔在途包括一个已经接收、正在等待 RREADY 消费的读结果。由于两个方向各有一组寄存器，这个容量约束并不把读写加总为一笔；主设备可以同时各发一笔并让它们独立结束。

这种保守的 READY 策略也限定了吞吐率。没有背压时，通道空闲期间可提前看到 READY；如果 BREADY 在 BVALID 产生后立即保持为高，B 响应最早在下一个边沿被消费，写接收端在响应完成后重新开放，主设备需要遵循当前可见的 READY 再发送下一笔。实现没有承诺每周期接收一笔，也没有把某个特定平均吞吐率写入接口契约。读通路可在 RVALID 被接收的下一周期重新接收 AR。若性能指标要求连续事务，应先定义指标是峰值、平均还是最坏延迟，再调整队列深度和响应调度，并以压力测试验证，而不是只将 READY 改成常数一。

主从双方必须对 resetn 的作用范围达成一致。同步复位清空本模块内部的配对状态，所以复位前只完成 AW 而没有 W 的事务不会在解除复位后继续等待；反过来，孤立的 W 也一样丢弃。若主设备没有同时复位并在复位后仍保留 VALID，它会在模块重新开放 READY 后提交一个新的握手，不能把这种行为视为旧请求的恢复。集成设计应让总线复位策略与主设备软件驱动相符，并检查外设状态是否允许 CTRL 清零。若软件复位只重启外设而不重置总线从设备，则应额外定义该软件复位与在途请求的交互，不能把它和这里的 aresetn 混为一谈。

错误返回也有边界。主设备收到 SLVERR 后可以报告访问失败，但重试规则属于上层软件或系统策略。对于这里的普通 CTRL，合法写在请求两半到齐时提交一次，随后响应保持到握手；非法写不提交。若以后给寄存器增加了“写 1 发脉冲”或“读清除”行为，失败和重试的副作用分析就更严格：读值必须在何时清除，复位是否会重复发脉冲，写响应背压期间操作是否已经发生，都要在寄存器规范中逐项写明。验证最好同时观察外部 side effect 的计数和 AXI 响应，而不只检查 RDATA 或 BRESP。

7. 规范依据

协议依据为 Arm 官方文档 AMBA AXI and ACE Protocol Specification，IHI 0022H，重点阅读 A3 章的通道握手规则及 B1 章 AXI4-Lite（B1.1 定义、信号列表、总线宽度、写选通）。文档列明 Lite 事务长度为 1、固定 32/64 位数据宽度、BRESP/RRESP 不支持 EXOKAY，并说明写选通用于指示有效字节通道。本文的寄存器地址、SLVERR 用法、单项队列策略和同步复位语义属于本案例工程约定，而非 Arm 规范强制规定。
